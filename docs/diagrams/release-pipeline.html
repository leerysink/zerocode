ZeroCode 发布流水线 · 一键上线与自动回退

点「发布」之后由平台代跑的七步。任何一步失败，都不会打断同事正在用的那个版本。

版本号 b<YYYYMMDDHHmmss>，字典序即时间序 每应用一对端口，取自池 8210–8399 running 才写进 routes.json
1

发布前检查

preflight
  • 点名阻断项：文件名、app.json、结构漂移
  • 破坏性变更必须人工确认
  • 可自修项静默补齐反代与镜像源
2

镜像构建

build
  • 前后端各出一枚版本化镜像
  • zc-{slug}-*:prod-版本
  • 依赖镜像源按出包策略注入
3

数据库供给

provision
  • 缺 prod 分库时现场建库建角色
  • 口令落进 deploy/.env，不进代码
  • 凭据归属登记在平台库
4

数据库迁移

migrate
  • sqlchange 只补跑没跑过的
  • 数据轨 D* / 结构轨 V* 双轨
  • 迁移不过则正式栈不启动
第一行跑完接第二行 · 全程 /ws/deploy 逐步推进度条
5

正式栈启动

deploy
  • compose up -d zc-{slug}-prod
  • 旧版本在新栈就绪前不中断
  • 端口与路由按新版本接上
6

联合体检

health
  • 前端页与后端 /api/health 双探针
  • 体检不过：容器保持运行供排查
  • 通过即视为该版本可交付
7

发布记账

record
  • 版本、地址、状态落库留痕
  • schema 快照归档，供下次 diff
  • 进「发布历史」可按版本回滚
✓

拿到可访问地址

同事直接打开
  • 局域网 http://IP:端口
  • 配好网关后 https://应用名.域名
  • 再点「发布到商店」即全团队复用
任一步失败

自动回退上一版本

build / migrate / health 任一处抛错，平台立刻把正式栈指回上一个通过体检的版本，不会出现「地址在、页面挂了」的中间态。

失败留痕，不当成成功

失败步骤连同日志进发布历史；地址不会指向一个没体检过的版本，网关路由只收 running 的栈。

事后一键回滚

发布历史逐版本列着时间、状态与地址，点回滚即切回该版本，不需要重新走一遍构建。

多版本保留

按 keep-5 保留最近数枚版本镜像与结构快照，回滚有货可取，不被下一次发布挤掉。

独立实例升级

商店升级先在真数据的克隆库上预演迁移，通过才动正式库；各实例数据独立、互不可见。

现场产物不被覆盖

升级只替换 backend/、frontend/ 等三棵，部署根上的现场产物、凭据与数据不碰。

实时可观测

日志抽屉先拉历史再订阅当前；资源监控看 CPU / 内存 / 库 / 工作区，停炉照实写「未采集」。

步骤名逐字取自进度条 PublishModal.STEP_LABELS 与后端 prod.py:STEPLIST 预览（dev）与正式（prod）是两套互不影响的栈：预览怎么折腾都不动线上
