# zerocode 部署发布套件（v2）— 06 应用数据库供给（PG）

- 日期：2026-09-18
- 关联：00 总览（D7）、01 应用模型、03 Dev 预览、04 Prod 发布、07 sqlchange

## 1. 需求背景

D7 已定：**复用 `zerocode-pg16` 唯一实例，按应用分库**（`<slug>_dev` / `<slug>_prod`，独立角色），不每应用起独立 PG 容器——小工厂机器跑不动一堆 PG。用户对数据库零感知：建应用自动有库，连接自动注入，删应用可选删库。

## 2. 用户故事

- S-06-1 王厂长建"来料登记"应用，后台自动多了 `lailiao_dev/lailiao_prod` 两个库，AI 生成的代码里看不到任何密码。
- S-06-2 dev 里 AI 让他试错录了一堆脏数据；发布后正式库干干净净，两边互不影响。
- S-06-3 应用删掉后，两个库也清掉了，PG 里不留垃圾。

## 4. 详细设计

### 4.1 命名与规模边界

- 标识：slug（`[a-z][a-z0-9]{1,39}`）→ 库名/角色名 = `<slug>_dev|<slug>_prod`（最长 45 字符，远低于 PG 63 上限；全部小写无需引号）。
- 实例容量参考：8210 段最多 95 个应用 × 2 库，单机 PG 实例足够；真到量级属多机部署（非目标）。

### 4.2 供给流程（幂等，失败即中止并回滚已做步骤）

```
provision(env):   # env ∈ {dev, prod}
  1 SELECT 检查 role <slug>_env / database <slug>_env 是否存在
  2 不存在则：CREATE ROLE … LOGIN PASSWORD '<24位随机>'
             CREATE DATABASE <slug>_env OWNER <slug>_env
  3 GRANT：OWNER 即全部；确认 public schema 归属角色
  4 记录凭据：app_config['dbcred.<slug>.<env>'] = {user, password, dbname}
  5 渲染/更新 deploy/.env 对应段（DEV_* / PROD_*）
```

- 密码生成：`secrets.token_urlsafe(18)`（24 字符，含字母数字，PG 密码安全字符集内，无引号冲突）。
- `CREATE DATABASE` 不能在事务内：逐条用 autocommit 连接执行（v1 conftest 已有同款经验）。
- 供给由平台管理员连接执行（superuser 或平台专用账号），应用容器只见自己的角色。

### 4.3 连接串契约（compose 注入，与 02 §4.2 对应）

| 栈 | 环境变量 |
|---|---|
| vue3-fastapi | `DATABASE_URL=postgresql+asyncpg://<user>:<pwd>@zerocode-pg16:5432/<db>`（容器网络内服务名/容器名访问，不走宿主 5433 端口映射——PG 容器加入应用 compose 网络的 `external` 网络，见 4.4） |
| vue3-node | `DATABASE_URL=postgresql://<user>:<pwd>@zerocode-pg16:5432/<db>` |
| vue3-springboot | `SPRING_DATASOURCE_URL=jdbc:postgresql://zerocode-pg16:5432/<db>` + `SPRING_DATASOURCE_USERNAME/PASSWORD` |
| static | 无 |

### 4.4 网络拓扑

- zerocode-pg16 现仅映射宿主 5433；应用容器需要网络可达 PG。
- 方案：每个应用 compose 声明 `networks: { zcnet: { external: true } }`；平台首次需要时创建外部网络 `zcnet`，并把 `zerocode-pg16` 接入（`docker network connect zcnet zerocode-pg16`，幂等）。应用容器间互访走 compose 默认网络，PG 访问走 `zcnet`，主机名 `zerocode-pg16`。
- 好处：PG 端口无需对宿主新开映射，凭据不出 Docker 网络；dev/prod compose 同构。

### 4.5 删除与护栏

- 删库顺序：`REVOKE` 新连接 → `pg_terminate_backend` 断开活动会话 → `DROP DATABASE` → `DROP ROLE`（角色拥有对象已随库删除；跨库对象不存在——角色仅 OWN 自己的库）。
- 误删防线：只允许经"删除应用"流程触达（01 FR1-07），无独立删库入口；输入 slug 双确认。
- 应用库**不注册**进平台 changelog 体系——迁移历史在每库自身的 `sqlchange_history`（07），两套体系严格分离。

## 5. 接口

| 方法与路径 | 说明 |
|---|---|
| （内部）`provision.dev/prod` | 由创建应用/发布流水线调用，不单独暴露 REST |
| `GET /apps/{id}/databases` | 两库信息：库名/角色/大小/连接数/`sqlchange_history` 计数 |
| `POST /apps/{id}/databases/{env}/rotate-password` | FR6-06（返回是否需要重启对应环境） |

## 6. 错误处理

| 场景 | 行为 |
|---|---|
| PG 容器未启动 | 供给前置检查失败：中文引导启动 PG 容器（复用 D9 体检），创建应用/发布中止 |
| 角色已存在（重装/半失败恢复） | 幂等跳过创建；凭据丢失时走"重新生成密码"路径而非报错 |
| 密码含 PG 特殊字符 | 生成字符集已规避；外部导入场景连接串统一 URL-encode |
| DROP 时连接无法断开 | 重试 3 次后报"仍有活动连接（可能是 dev 预览未停）"，提示先停止预览 |
| .env 与 app_config 凭据不一致（手改过） | 启动环境前校验：以 app_config 为准回写 .env，UI 提示已修复 |

## 7. 验收标准

1. 创建应用后 `lailiao_dev`/`lailiao_dev` 角色存在且 OWNER 正确；重复创建同 slug 被拒，重建流程幂等通过。
2. 用 `<slug>_dev` 角色连接 `<slug>_prod` 被拒绝（权限隔离实测）。
3. 发布后应用后端实际写入的是 prod 库；dev 预览写入的是 dev 库；两边数据互不可见。
4. 删除应用勾选删库：两库两角色消失，活动连接场景有明确提示。
5. 全链路（AI 上下文、app.json、UI）不出现数据库密码明文。
