## 1. 背景与问题

zerocode v1 已交付：本地单机 Web 应用（FastAPI :8100 + Vue3，PG 16 容器 :5433），用户通过聊天让 AI 在工作区里生成代码、读写文件、双向提问。

当前断点：**生成的代码只是躺在目录里的文件**。小工厂用户没有部署能力——不会装 Node/Maven、不会写 Dockerfile、不会建数据库、更不会把它们连起来跑起来。AI 生成 → 用户可用的"最后一公里"缺失。

v2 目标：补上这一公里。用户在聊天框里把项目"说"出来，zerocode 负责把它变成**一个可以在局域网里被同事直接打开网址访问的应用**。

## 3. 目标与非目标

### 目标（v2 交付）
1. **一键发布**：生成的代码一键打包成 Docker 镜像并启动，产生局域网可访问 URL。
2. **实时预览**：AI 编辑代码期间，dev 环境热重载，zerocode 界面内嵌预览。
3. **应用专属数据库**：每个应用自动获得独立 PG 库（dev/prod 两套），凭据自动注入。
4. **技术栈默认化**：大型程序 Vue3 + Spring Boot 3；小型程序 Vue3 + FastAPI / Vue3 + Node / 纯前端，三选一；数据库一律 PostgreSQL。
5. **双套环境**：一份代码，dev（预览）与 prod（发布）两套 Docker 运行环境，数据库物理隔离。
6. **SQL 版本化**：应用所有数据变更放应用内 `sqlchange/` 目录，dev 启动与 prod 发布时增量自动执行。

### 非目标（v2 明确不做）
- 公网发布、域名、HTTPS、内网穿透（局域网内用 IP:端口直接访问）。
- 推送到云服务器 / SaaS 多租户托管。
- CI/CD 流水线、多机部署、负载均衡。
- 应用数据自动备份（文档提供手动 `pg_dump` 命令建议，工具化留后续）。
- 应用内权限/登录体系的设计（由 AI 按需求生成，模板不强制）。
- zerocode 平台自身做多人/鉴权（维持单机单用户）。

## 4. 核心概念与术语

| 术语 | 定义 |
|---|---|
| 应用（App） | zerocode 管理的可部署单元 = 一个遵循应用工程结构的工作区（根目录含 `app.json`），对应平台库 `app_project` 一条记录 |
| slug | 应用标识：`[a-z][a-z0-9]{1,39}`，用于目录名、库名、镜像名、端口分配 |
| dev 套 | 开发预览环境：源码 bind-mount + 热重载 + `<slug>_dev` 库，端口 = 奇数段 |
| prod 套 | 生产发布环境：镜像运行 + `<slug>_prod` 库，端口 = 偶数段 |
| 发布（Publish） | 构建 prod 镜像 → 供给 prod 库 → 执行 sqlchange → 启动 prod 套 → 健康检查 → 生成 URL 的完整流水线 |
| 版本 | 一次发布的产物标识 `b<YYYYMMDDHHmmss>`，镜像 tag 携带；保留最近 5 版可回滚 |
| sqlchange | 应用内 SQL 变更目录，`V<YYYYMMDD>_<两位序号>_<说明>.sql`，由一次性 migrator 容器增量执行 |
| sqlrunner | 平台提供的一次性迁移执行镜像 `zerocode-sqlrunner:1`（psql + 执行脚本），dev/prod compose 均引用 |

## 5. 总体架构

```
浏览器
  ├── zerocode 平台 UI (:8100, 127.0.0.1)  ← 单机操作入口，管理一切
  │      聊天页（AI 生成）＋ 应用页（管理/预览/发布）
  ▼
FastAPI 后端 (:8100)
  ├── app/agent/*          v1 既有：AI 循环、文件工具（不动）
  ├── app/deploy/*         v2 新增：DeployEngine
  │      engine.py   生命周期状态机（dev 启停 / publish 流水线 / 回滚）
  │      compose.py  dev/prod compose 渲染与校验（模板 + app.json + 端口 + 凭据）
  │      ports.py    端口分配器（8210-8399 成对分配）
  │      provision.py PG 分库供给（建库/建角色/授权/删除）
  │      runner.py   docker CLI 子进程封装（compose build/up/down/logs）
  │      history.py  发布记录（deploy_record）
  ├── app/api/apps.py      REST /api/apps/*
  └── app/api/deploy_ws.py WS /ws/deploy/{app_id}（构建/运行日志实时下行）
  ▼
Docker（Docker Desktop）
  ├── zerocode-pg16（宿主 :5433，容器网络内 :5432；经外部网络 zcnet 供应用容器访问）
  │      zerocode（平台自身）        changelog/ 管理平台表
  │      <slug>_dev / <slug>_prod   每应用两库，独立角色
  ├── 应用 dev 栈：frontend(vite) + backend(hot-reload) + migrate(sqlrunner)   → :8211
  └── 应用 prod 栈：frontend(nginx) + backend(镜像) + migrate(sqlrunner)      → :8210
```

**数据流（一个应用的完整生命周期）**：

```
新建应用（向导：名称/规模/栈） → 生成 app.json + 脚手架铺底 + 分配端口对 + 建 dev 库
   → 聊天生成/迭代代码（AI 契约注入：目录约定、sqlchange 规则、health 要求）
   → 「预览」→ dev 栈启动（sqlrunner 先跑 dev 库迁移）→ iframe 内嵌预览，热重载
   → 「发布」→ prod 镜像构建 → prod 库供给 → sqlrunner 跑 prod 迁移 → prod 栈启动 → 健康检查
   → 展示 http://<内网IP>:8210，同事可访问
   → 再迭代 → 再发布（新版本镜像，旧版本保留 5 份可回滚；数据库永不回滚）
```

## 6. 关键决策记录

| # | 决策点 | 结论（已确认） |
|---|---|---|
| D1 | 部署目标 | 本机/局域网，URL = `http://<内网IP>:<端口>` |
| D2 | "开发/生成两套" | 一份代码 + dev/prod 两套 Docker 运行环境，数据库分库隔离 |
| D3 | 大型栈 | Vue3 + Spring Boot 3 单模块（JDK 17 / Maven / MyBatis-Plus） |
| D4 | 小型栈 | Vue3+FastAPI（主推）、Vue3+Node(Express)、纯前端静态页，向导按规模选 |
| D5 | URL 形态 | 每应用独立端口，仅前端端口对外 |
| D6 | SQL 规范 | 应用内 `sqlchange/`；zerocode 平台自身继续用 `changelog/`，互不干扰 |

补充推荐（已确认采纳）：

| # | 决策点 | 结论 |
|---|---|---|
| D7 | 应用数据库供给 | 复用 `zerocode-pg16` 同实例分库（`<slug>_dev`/`<slug>_prod` + 独立角色），不每应用起独立 PG 容器 |
| D8 | 发布历史 | 镜像 tag 版本化，保留最近 5 版，一键回滚；**数据库不回滚**（sqlchange 无自动回滚，回滚仅回代码） |
| D9 | 环境体检 | Docker 未启动/不可用时给出中文引导（含一键启动 Docker Desktop），不甩报错堆栈 |
| D10 | 生成方式 | 脚手架模板铺底（向导初始化可运行骨架）+ AI 增量开发，不做 AI 从零全量生成 |

## 7. 平台自身改动面

| 层 | 改动 |
|---|---|
| 后端新模块 | `app/deploy/`（engine/compose/ports/provision/runner/history + sqlrunner 镜像构建脚本） |
| 后端 API | `app/api/apps.py`、`app/api/deploy_ws.py`；`app/main.py` 挂路由 |
| 平台库（走 `changelog/V<YYYYMMDD>_*.sql`） | 新表 `app_project`、`deploy_record`；`app_config` 新增 `deploy.*` 键（详见 01/05/06） |
| 前端 | 新增应用页 AppsView、新建应用向导、聊天页预览页签、配置页环境体检卡（详见 08） |
| v1 既有能力 | 工作区/会话/文件工具/双向提问/静态托管全部复用，不改动语义 |

## 8. 全局错误处理原则

1. **面向零经验用户的话术**：所有部署链路错误必须给出"发生了什么 + 你可以做什么"的中文提示（如 Docker 未启动 → 检测并提供一键启动按钮），技术细节放可展开的日志区。
2. **prod 优先可用**：发布失败时旧版本保持运行不中断；健康检查不过则自动回退到上一版本镜像并标记发布失败。
3. **数据不可逆操作双确认**：删除应用、删除数据库要求输入 slug 确认。
4. **状态可观测**：dev/prod 状态机每一步变化通过 WS 推送；所有构建/运行日志可在 UI 查看与回看。

## 10. 端到端验收标准（v2 整体）

1. 全新机器（装好 Docker Desktop）安装 zerocode → 向导建"小型/FastAPI"应用 → 聊天生成"来料登记"（含建表）→ 预览可用 → 发布成功 → 同一台局域网内另一台电脑用 `http://<IP>:8210` 访问并完成一次数据录入，重启 zerocode 后重新启动应用数据仍在。
2. 同场景建第二个应用，两应用端口/数据库/容器完全隔离，可同时运行。
3. 大型栈（Vue3+Spring Boot 3）走通同样的生成→预览→发布链路。
4. 修改代码 + 新增 sqlchange 文件后再次发布：新功能生效、旧数据保留、可回滚到上一版本。
5. Docker 未启动时：每一步操作给出中文引导而非报错堆栈。
