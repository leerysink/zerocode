# zerocode 部署发布套件（v2）— 01 应用模型与项目结构

- 日期：2026-09-18
- 关联：00 总览（决策 D1/D2/D10）、02 技术栈模板、06 数据库供给

## 1. 需求背景

v1 的"工作区"是任意目录（用户手输/浏览选择），平台对它一无所知。要支撑"一键打包发布"，平台必须理解一个可部署单元的**固定结构与元数据**——这就是"应用"：一个平台认识、能初始化、能预览、能发布的工程目录。

## 2. 用户故事

- S-01-1 王厂长点「新建应用」，填中文名"来料登记"、选"小型/Vue3+FastAPI"，平台自动建好工程目录和数据库，他不需要知道目录里有什么。
- S-01-2 会话里 AI 生成的每一行代码都落在应用目录的正确位置；用户问"我的项目在哪"，界面直接给路径并一键打开。
- S-01-3 用户把应用目录整个拷到另一台装了 Docker 的机器，用 `docker compose up` 也能跑（可迁移性）。

## 3. 功能需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR1-01 | 新建应用向导：输入显示名（中文可）、规模（small/large）、栈（随规模联动），slug 自动生成可改，应用根目录默认 `<apps_root>/<slug>` 可改 | P0 |
| FR1-02 | slug 规则：`[a-z][a-z0-9]{1,39}`，自动去重（冲突时追加序号）；显示名可任意中文 | P0 |
| FR1-03 | 创建应用 = 原子动作：建目录（从脚手架模板铺底）→ 写 `app.json` → 平台库 `app_project` 落记录 → 分配端口对（05）→ 供给 dev 库（06）；任一步失败回滚已建目录与记录 | P0 |
| FR1-04 | 应用列表页展示全部应用：名称/规模/栈/两套环境状态/端口/URL/操作 | P0 |
| FR1-05 | 应用与 v1 工作区的关系：应用必有一个关联 workspace（root=应用目录）；普通工作区保持 v1 行为，根目录无 `app.json` 即非应用 | P0 |
| FR1-06 | 应用元数据查看：app.json 内容、目录结构、端口、数据库、版本历史入口 | P1 |
| FR1-07 | 删除应用：停止 dev/prod 栈 → 双确认（输入 slug）→ 删容器/镜像/平台记录，数据库删除为独立勾选项（默认勾选，见 06） | P0 |
| FR1-08 | 重新扫描：平台启动时核对 app_project ↔ 目录（app.json 存在性/一致性），不一致的标记 `warning` 并在列表提示修复 | P1 |

## 4. 详细设计

### 4.1 应用工程目录结构（生成物约定）

```
<apps_root>/<slug>/                 # 应用根 = workspace root
├── app.json                        # 应用清单（本文档 4.2）
├── frontend/                       # Vue3 工程（四种栈都有）
│   ├── src/
│   ├── package.json
│   ├── vite.config.js
│   └── Dockerfile                  # 发布用：node build → nginx 静态
├── backend/                        # 后端工程（static 栈无此目录）
│   ├── （FastAPI: app/main.py, requirements.txt, Dockerfile）
│   ├── （Express:   src/server.js, package.json, Dockerfile）
│   └── （Spring:    pom.xml, src/main/java/..., Dockerfile）
├── sqlchange/                      # SQL 变更目录（07 详细规范；static 栈保留空目录+README）
│   └── V20260918_01_init.sql
├── deploy/
│   ├── dev-compose.yml             # 由平台渲染生成，用户可查看
│   ├── prod-compose.yml
│   └── .env                        # 端口/库名/凭据（平台生成，随目录迁移）
└── README.md                       # 面向用户的说明（含局域网访问地址、常见问题）
```

### 4.2 app.json（schema `zc-app/1`）

```json
{
  "schema": "zc-app/1",
  "name": "来料登记",
  "slug": "lailiao",
  "scale": "small",
  "stack": "vue3-fastapi",
  "ports": { "prod": 8210, "dev": 8211 },
  "database": {
    "dev":  { "name": "lailiao_dev",  "user": "lailiao_dev" },
    "prod": { "name": "lailiao_prod", "user": "lailiao_prod" }
  },
  "health": { "frontend": "/", "backend": "/api/health" },
  "createdAt": "2026-09-18T10:00:00+08:00",
  "platformMin": "1.1"
}
```

- 密码**不写入 app.json**（清单可能被用户分享），密码只存在于平台库 `app_config`（06）与 `deploy/.env`。
- `health.backend` 随栈固定（FastAPI/Express `/api/health`、Spring `/actuator/health`、static 无）。
- 平台是 app.json 与 `deploy/**` 的唯一写入方（AI 的文件工具对 `app.json` 做写保护，防止模型改坏结构；校验失败拒绝启动环境并提示重建）。**勘误（终审 M-3）**：`deploy/**` 读写皆平台专属——目录含明文凭据（`deploy/.env`），AI 文件工具与 UI 文件读取一律拒读（`is_secret_read` 收口）；`app.json` 读放行（AI 需看清单）。

### 4.3 平台库 `app_project`（DDL 走平台 changelog/）

```sql
CREATE TABLE IF NOT EXISTS app_project (
    id            BIGSERIAL PRIMARY KEY,
    workspace_id  BIGINT NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    name          VARCHAR(100) NOT NULL,
    slug          VARCHAR(40)  NOT NULL UNIQUE,
    scale         VARCHAR(10)  NOT NULL,          -- small | large
    stack         VARCHAR(20)  NOT NULL,          -- static | vue3-fastapi | vue3-node | vue3-springboot
    prod_port     INT NOT NULL UNIQUE,
    dev_port      INT NOT NULL UNIQUE,
    status_dev    VARCHAR(20) NOT NULL DEFAULT 'stopped',  -- stopped|starting|running|unhealthy|error
    status_prod   VARCHAR(20) NOT NULL DEFAULT 'stopped',  -- stopped|publishing|running|unhealthy|error
    current_version VARCHAR(40),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- 规模与栈联动：`large` ⇒ `stack=vue3-springboot`（锁定）；`small` ⇒ 三选一。
- `status_*` 是平台侧状态机的事实来源；容器实际状态由 Docker 为准，UI 提供"刷新实际状态"。

### 4.4 与 AI 聊天的关系（应用契约注入）

激活工作区是应用目录时，agent system prompt 追加**应用契约**（详见 02 §5）：目录约定、栈规范、`sqlchange/` 强制规则、health 要求、env 配置读取方式。AI 不负责建 compose/端口/数据库——这些由平台向导与引擎负责，AI 的文件工具对 `deploy/` 目录读写皆禁（终审 M-3 勘误：原文「只读」许可读，凭据可进模型上下文，已收紧为密文读禁；`app.json` 读仍放行）。

### 4.5 脚手架铺底（D10）

向导创建应用时从平台内置模板（`app/templates/<stack>/`，见 02）复制骨架：可运行的最小前后端（含 health、`sqlchange/V…_01_init.sql` 示例、Dockerfile、README）。**AI 的第一句话面对的是一个已经能预览的空应用**——首次生成即"在骨架上实现功能"，可靠性远高于从零生成。

### 4.6 删除与再扫描

- 删除顺序（事务性尽量保证，失败逐条汇报）：`docker compose down`（dev/prod）→ 删镜像（含保留的历史版本）→ 可选删两库+两角色（06）→ 删 `app_project` 记录 → 删目录（Windows 占用时提示手动删除路径）。
- 再扫描（FR1-08）：启动时逐条核对 `app_project`：目录存在？app.json 可解析？端口仍登记？workspace 存活？问题项列表展示"一键修复"（重建 app.json / 解除关联 / 移除记录）。

## 5. 接口设计（本域部分，REST 前缀 `/api`）

| 方法与路径 | 说明 |
|---|---|
| `POST /apps` | 新建应用 `{name, slug?, scale, stack, root?}` → 201 `{app}`（含端口/库名），失败 400/409 带原因 |
| `GET /apps` | 应用列表（含状态、端口、URL、current_version） |
| `GET /apps/{id}` | 应用详情（app.json 解析结果 + 数据库 + 最近发布） |
| `DELETE /apps/{id}` | body `{confirmSlug, dropDatabases}` → 执行删除流水线 |
| `GET /apps/{id}/structure` | 目录结构树（复用 v1 `/fs/tree`，限定应用根） |

WS `/ws/deploy/{app_id}` 的事件与状态机定义见 03/04。

## 6. 错误处理

| 场景 | 行为 |
|---|---|
| slug 冲突/非法 | 409/400，返回建议 slug |
| 目录已存在且非空 | 409，要求换 slug 或换目录 |
| 模板缺失（栈模板文件损坏） | 创建中止并回滚，报"平台安装不完整，请重装模板" |
| app.json 校验失败（用户手改坏） | 应用标 `warning`，禁止启动环境，提供"按平台库记录重建 app.json" |
| 删除时容器删除失败 | 记录失败项继续后续步骤，结果页列出需手动处理的资源 |

## 7. 验收标准

1. 向导创建 small/vue3-fastapi 应用后：目录结构完整可运行（`docker compose -f deploy/dev-compose.yml up` 可起）、`app.json` 合法、`app_project` 一条记录、端口对已分配、`<slug>_dev` 库已建。
2. large 规模创建时栈锁定为 vue3-springboot，且脚手架为 Spring Boot 3 骨架。
3. AI 对 `app.json` 与 `deploy/` 的写请求被拒绝并提示（文件工具写保护测试）。
4. 删除应用：容器/镜像/记录清理干净（选删库时 `<slug>_dev/_prod` 与角色消失），再扫描无残留告警。
5. 平台重启后再扫描：删除目录但保留记录的应用被标 `warning`。
