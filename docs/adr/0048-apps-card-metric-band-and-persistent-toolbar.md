# 0048 应用卡片改成数据仪表卡：批量 summary 端点 + 常驻工具条 + CPU 环

「我的应用」页原先是 4 个行内按钮 + 一个把所有低频动作（预览/监控/历史/工程目录/日志/重命名/DB/移动端/发布到商店）
塞进 ☰ 折叠菜单的卡片。两个问题叠在一起：**动作要点开才看得见**（16 个动作里用户常驻只认得 4 个），
**卡片没有任何运行信息**（想知道这个应用现在忙不忙得逐一点开资源监控弹框），
**页头还和卡片同权重**（18px 标题 + 裸文字「返回」，一眼扫不出这是总览页）。本 ADR 定四件事：

1. **动作分层改向**：卡片静息保留 4 个环境动作（测试环境 启停/重启 · 生产环境 发布/启停），其余
   **10 个动作摊在卡底的常驻工具条上，一排图标默认就在**；动作名做成悬停气泡 + `aria-label`。
   环境动作行本身压成**两段胶囊**（状态点 + `dev`/`prod` 字母 + 两个图标按钮），整条约 250px，
   一行排完不折行——原先两组「全称标签 + 全称按钮」需要 ~480px，而卡片内容区只有 440px，必然折成两行。
   分组交给胶囊外壳，**中间那条竖线撤掉**。**☰ 只剩两个动作：重建 dev、删除应用**。理由不是空间，是误点代价：
   这两个各自带一次确认框且会删数据，平铺进工具条等于把「不可逆」的权重摊薄到和「复制地址」同一排。
   动作节点始终常驻 DOM（收起靠的是 `max-height` 那套已废弃，见备选方案）。
2. **仪表卡取数走新增的批量端点** `GET /api/apps/metrics/summary`：一页一次请求，回当前账号可见的每个应用
   一条 `{app_id, prod_status, cpu, memory, db_size, workspace_size, series:{cpu, memory}}`。
   窗口固定 **近 1h 折成 ≤24 桶**（≈150 秒一点，30 秒轮询下曲线真在动），曲线只带 cpu/memory 两族——
   磁盘是慢变量，画成 sparkline 是一条假直线。权限**只有一条判据**：沿用 `app_service.list_apps` 的 owner 过滤，
   不在端点里重写一遍 SQL 权限；别人的应用不是 404 而是**不出现在 items 里**（批量端点没有「那一个」可供 404，
   缺席本身就是不暴露存在性的口径）。
3. **环画 CPU 占用，不做健康分**：中心环 = prod 栈常驻容器汇总的 CPU %（多核可超 100，环只画到 100、数字照实）。
4. **页头做成总控区（hero）**：整行包进淡主色渐变条幅，标题 18→22px + 应用数徽标，「返回」从裸文字链接
   改成描边 chip；条幅下沿一排统计 `应用 / 运行中 / 进行中 / 已停止 / 异常 / 平均 CPU`。
   两条硬口径：**四桶必须严丝合缝盖全 `status_prod`**（running · starting+publishing · stopped · unhealthy+error），
   加起来不等于总数就是骗人；**平均 CPU 只对采到值的活应用求平均，一个都没采到写 `—`**，写 `0.0 %` 会被读成「很闲」。
   数字全从已加载的 `listApps` + `metrics/summary` 现算，**不新增后端聚合**——页本来就为这两个请求付过钱。

## 停炉语义（三处必须同口径）

prod 非 `running/unhealthy` 时没有实时值。后端 summary 把 `cpu`/`memory` 连同 `series` **一起归空**
（残留读数画成趋势比空白更坏），磁盘两族照实返回；前端据此显示 **`停炉未采集` / `未采集`** 而不是 `0.0 %`，
环退成灰轨。这与 `metrics_current` 既有口径一致，只是把「停炉」从数值空态升级成一句会说人话的说明。

## 备选方案

- **双排常驻按钮**（8 个动作全平铺，不需要悬停）：可达性最好。否决理由是可读性——两排同权重按钮会把
  「启停/发布」这四个真正常驻动作的视觉主次抹平，而它恰好是唯一跨环境、有后果的四个。
- **悬停滑出工具条 + 图钉兜底**（本 ADR 的第一版实现）：卡片更矮、hover 时有动效。**废掉的真实原因**：
  「要点到才有东西」把可发现性押在悬停上，图钉只是给触屏和键盘补的后门，而用户第一次进页面看不到动作就是看不到。
  换成常驻一排图标后，卡片高度多付 ~38px，换回 10 个动作永远可见。
- **环画综合健康分**：一屏一个数最直观。平台**没有内存上限/配额，也没有 uptime 指标**，任何 (cpu, mem) → 单一分数
  的映射都是编数；编出来的数还会被当成平台承诺的 SLA 读。改成只画真实采集值。
- **逐应用调 `/{id}/metrics/current` + `history`**：不改后端。代价是 N 卡 × 2 端点 × 每轮轮询，
  一个 20 应用的账号一轮就是 40 个请求，且列表页首屏要等最慢的那个应用。压成 1 个请求后
  `DISTINCT ON` 一条 + 桶聚合一条，共 2 条 SQL 打完。
- **环境动作行保留中文全称标签**（现状版）：最直白，但一行放不下必然折成两行——这正是本次要修的病。
  全称没消失，只是退到胶囊的 `title` 和按钮的 `aria-label`/气泡里，读的人要时仍在，占位的人不用看。
- **`display:none` 收工具条**：省掉动画。但它同时把动作从 a11y 树和 Tab 序列里摘掉，无论何时都不该用。
- **页头统计另开一个后端聚合端点**：数字更权威。否决——它们要的就是列表页已经拿到的那两份数据
  （`listApps` 的状态 + `metrics/summary` 的 CPU），再开一个端点等于给同一个事实长出第二套口径，
  还要多付一次请求。只有当统计需要跨账号/跨时间窗（本页面做不到的事）时才值得动后端。
- **`/apps/{app_id}/metrics/summary`**（挂在单应用前缀下）：形状更整齐。选 `/api/apps/metrics/summary` 是为了
  和单应用取数在路径上分开——`/{app_id}` 是 int 路径参数，字面量 `metrics` 落在同一段会依赖声明顺序才不被吞，
  没必要留这种「靠路由注册顺序保正确」的地雷（现有 3 段路由已逐个核过不与 `metrics/summary` 同形）。

## 影响

- 后端：`app/api/metrics.py` 新增 `metrics_summary` 与 `_latest_batch`/`_series_batch`，常量
  `SUMMARY_WINDOW/SUMMARY_WINDOW_LABEL/SUMMARY_MAX_POINTS/SUMMARY_SERIES_KINDS`；单应用两个端点不动。
- 前端：`AppsView.vue` 卡片重构（仪表带 + 环境胶囊动作行 + 常驻工具条），☰ 由 11 项缩到 2 项；
  四个环境动作由 `a-button` 换成原生 `button`（图标 + 气泡）；页头换成 hero 条幅（`.zc-hero` + `.zc-stats`，
  `status_prod` 四桶与平均 CPU 在前端 `stats` computed 现算）；`utils/metricsFormat.js` 由 `MetricsModal.vue`
  与卡片共用一个格式化口径。`BackButton.vue` 本体不动（设置页共用），只在 `.zc-hero` 作用域里改成描边 chip。
- 测试：原「☰ 里有预览/日志/重命名…」两条断言随需求改写（动作换到工具条，不再在菜单里）；环境动作行的
  「靠竖线分组 / 全称文字」断言改成「两段胶囊 + 状态点跟 `statusColor` + 图标按钮带 `aria-label`」，
  「发布」按钮的定位钩子从 `.stub-a-button` 文字匹配换成 `.zc-act-publish`，并补了一条点击真接线
  （`devStart`/`devRestart`/`prodStop`）——换成图标按钮后，靠文字找按钮的旧断言就不再是回归网。
  新增 `tests/test_metrics.py` summary 段 6 条（含越权缺席、founder 全量、停炉归空、桶数上限）、
  `AppsView.test.js` 仪表卡段与页头段 6 条（分桶盖全 + 四桶之和等于总数 + 平均 CPU 跳过空读数 + 空列表不撒谎）。
  工具条/胶囊每个动作必须带出图标节点（`[role="img"]`）——图标名写错时
  Vue 只在 stderr warn 一个 undefined vnode，按钮会瞎成一排空白方块，这条断言就是钉这个的（已实测咬住）。
  分桶与平均的三条变异（异常并进已停止、进行中并进已停止、空读数当 0 计入平均）都实测跑红。
- 术语：见 `CONTEXT.md` 的「仪表带」「停炉未采集」「常驻工具条」「环境胶囊」「页头总控区」。
