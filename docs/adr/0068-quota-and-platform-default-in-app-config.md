# 0068 配额与平台默认都住 app_config 两级；平台级写收口管理员

- 状态：Accepted
- 日期：2026-11-23
- 关联：ADR-0067（管理员=创始人）、Ticket 007（用户级键前缀）、Ticket 003（owner 维度）、CONTEXT「实例」「平台默认」「账号配额」

## 背景

治理面要三样东西：每账号的应用创建上限、运行栈并发上限、管理员维护的默认配置。
现状已有两套各自成立的机制——`actor.max_sessions` 是一列整数，`app_config` 是
`(owner_user_id, key)` 两级表（owner NULL 打底、USER_PREFIXES 账号级覆盖）。
同时存在一条真实缺陷：注册事务把全局 `llm.*` **划归**创始人（UPDATE 而非复制），
第二个账号开箱拿不到任何模型配置，不自己填密钥就直连超时。

## 决策

1. **配额不住 `actor` 列，住 `app_config`**：新开 `quota.` 前缀归入用户级键
   （`USER_PREFIXES`），打底行留 owner NULL。平台默认一处生效、个别账号覆盖一行，
   读写接缝与 `llm.*` 完全同构。`max_sessions` 维持原列不搬迁——它管会话不是应用。
2. **「默认配置」= 平台级打底行**（owner NULL 的 `llm.*` / `agent.*` / `deploy.*` / `quota.*`），
   不引入配置模板表，也不是管理员代写别人的覆盖行。新账号开箱即用靠的就是这一层。
3. **平台级键的写入收口到管理员**，推翻 Ticket 007 那条「普通用户改 `agent.*` 影响全平台
   是既定取舍」。`set_many` 按键分流：用户级前缀写 owner 行，其余键要求调用者是管理员。

## 后果

- 设置页对普通账号出现一批**只读字段**（原先可编辑），文案与既有红线测试需同步。
- 每类资源限额从此是「加一个 `quota.<资源>` 键」而不是「加一列」，代价是配额值在库里
  是 JSONB、没有列级类型约束，读取侧必须自己收敛非法值。
- 平台默认一旦成为权威来源，管理员把 `llm.api_key` 填进 owner NULL 行就等于**代全平台
  付账**：所有未自配密钥的账号都会用它。这是本决策换来的能力，也是它的新增责任面。
