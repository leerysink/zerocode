# Android 分发改为平台构建的远程 URL WebView 壳

移动端 H5 已经能发布，但「可安装的 Android 包」一直停在 ADR-0039 的「平台代管用户上传的 APK」：
用户没有 HBuilderX / DCloud 工具链，弹框里的 APK 入口长期为空。决定把 Android 产物改成
**平台自己构建的远程 URL WebView 壳**：发布成功后异步构建，加载
`https://{slug}.{GATEWAY_DOMAIN}/h5/`（SSL 关时是 `nics.app_url` 的 IP 形态），产物仍写进 prod
的 `uploads` 卷，弹框下载/扫码。壳只负责把 H5 装进一个可安装的容器，不编译 uni-app 的
app-plus，也不提供任何原生能力；H5 更新不需要重出 APK。

为什么是远程 URL 而不是把 H5 打进 APK：离线包要接 app-plus 编译链、体积大、每次 H5 改动都要
重出包，且脱离了应用自己的域名与同源 `/api`；远程壳让 H5 继续享受网关、同源接口、发布流程和
资源监控，APK 只在「安装」这一步出现。代价是 APK 依赖网络且要求 prod 正在运行，这被接受。

构建走 Docker 里的 Android build-tools（aapt2 / d8 / apksigner），不用 Gradle/AGP：后者要在
构建期下载整套 Maven 依赖与 Gradle 发行版，镜像和失败面都大一圈；壳只有一个 Activity、一组
资源和一个 dex，build-tools 直出更小更快。包名由网关域名反写再加 slug（`zerocode.com` →
`com.zerocode.{slug}`），同一域名下天然唯一且稳定；图标默认按应用名首字生成，弹框可上传覆盖，
恢复默认会重建。壳版本与应用的发布版本无关，只在壳参数（名称/图标/启动地址/包名/壳代码修订）
变化或用户手动重建时递增。

## 备选方案

- **HBuilderX 云打包**（ADR-0039 的 R-1）：需要 DCloud 账号、实名、appid 与配额，仍是外部依赖；
  也没有解决 iOS 的空白。
- **离线 H5 壳**：可离线启动，但要 app-plus 编译链、H5 每次改动都重出包，且丢掉同源 `/api`
  与网关带来的统一地址。
- **只做 PWA**：iOS 可「添加到主屏幕」，但拿不到可安装的 APK，Android 分发的诉求没有落点。
- **继续人工上传**：平台零构建，但用户没有构建工具链，入口等于摆设（现状）。
- **Gradle/AGP 构建**：标准工程结构，但构建期网络与依赖体积远超本需求。

## 后果

- APK 只是薄壳：无网络或 prod 未运行时打不开；WebView 没有地址栏，HTTPS 证书无效会白屏。
- 包名绑网关域名：换域名等于换包名，已安装用户无法覆盖升级，只能卸载重装。域名视为长期稳定量。
- 平台统一 keystore：丢失后所有存量 APK 无法再升级（同包名不同签名），必须备份
  `data/apk_keystore/`。
- 首次构建要拉 Android SDK 与构建镜像，耗时长且依赖网络；失败只影响 APK，不影响 H5 发布，
  弹框可重试。
- 壳不含原生能力（相机/定位/推送/文件选择等），H5 里依赖这些的交互在 APK 内不可用；需要时
  再单独评估。
- ADR-0039 的「APK 不由平台构建、代管用户上传」被本 ADR 取代；同应用拓扑、H5 走 `/h5/`、
  账号复用等结论不变。
