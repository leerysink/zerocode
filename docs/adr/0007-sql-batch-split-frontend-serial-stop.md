# 0007 多语句 SQL：前端状态机拆分 + 批量端点逐条串行遇错即停

用户要在一个编辑器里写多条以分号分隔的 SQL 并一次执行。我们决定：前端用一个约 40 行的**纯函数状态机**按分号拆分执行段（跳过单/双引号、`--` 与 `/* */` 注释、`$$ ... $$` 函数体），把有序语句数组 POST 给新端点 `/{app_id}/db/{env}/sql/batch`；服务端在**同一个连接内**逐条串行执行，遇错即停、已成功的不回滚，逐条写审计，返回结果数组。现有单条 `/sql` 端点保留，继续服务「数据」页签的行内编辑。

被否决的方案：
- 整段原文直接发 PG（simple query）——改动最小，但会击穿现有 SELECT 护栏（无法外层包 `LIMIT 5001`），多结果集只拿得到最后一条。
- 整段包 `BEGIN ... COMMIT` 全或无——迁移脚本友好，但 `CREATE INDEX CONCURRENTLY` / `VACUUM` 不能在事务块内运行，且调试时用户常想保留已改的部分。
- 前端循环调用单条接口——零后端改动，但 `execute_sql` 每次都 `create_async_engine` + `dispose`（新建一次数据库连接），20 条就是建拆 20 次连接，且关页时难以中断。
- 后端用 pglast/sqlglot 真解析器拆分——准确性上限最高，但要新增 Python 编译依赖，且「只跑选中」也要往返。

批量端点内逐条沿用现有护栏：SELECT 仍加 `statement_timeout=15s` 并外层包 `LIMIT`，写/DDL 仍不加超时（用户承担）。

## 后果

- 「遇错即停 + 前面不回滚」意味着一次失败执行可能留下部分生效的数据，结果区必须显式写明「第 i/N 条失败，剩余 N-i 条未执行」，否则用户会误判整段没跑。
- 拆分的正确性风险落在前端状态机，边界用例（引号内分号、注释内分号、dollar-quoted 函数体、空段、只有尾分号、纯空白段）必须进单测。
- 审计从「一次点击一条记录」变为「一次点击 N 条记录」，操作历史抽屉的条数量级随之上升。
