# 0050 发布审批：被共享者发起、所有者批准即执行，只覆盖「发布新版本」

被共享者获得 prod 启停与移动端构建后，仍有一类动作会不可逆地切换线上版本：发布新版本。
本 ADR 定审批模型：

- **只有「发布新版本」走审批**。回滚、上架商店、小程序上传不在其列，仍仅所有者可用——
  把审批扩到所有对外生效的动作会让状态机与 UI 成倍膨胀，而这些动作本来就是所有者专属。
- **被共享者发起「发布申请」，所有者批准即执行**（异步发布，与现有 `POST /apps/{id}/publish`
  同一个引擎）。驳回须填理由，申请人可在待审期间撤回；同一应用同时只允许一条待审申请。
- 所有者自己发布不需要审批。

## 备选方案

- **批准后由所有者再手动点发布**：多一步人工动作，且审批与真正发布可能长时间脱节，
  「批准了但没发」会被申请人误读为已完成。
- **创始人审批**（与商店安装申请同一口径）：集中管控，但共享是所有者自己的协作关系，
  让平台管理员替所有应用的发布点头既慢又不合理。
- **只允许所有者发布，不建审批流**：最省实现，但需求明确要求被共享者能参与发布决策，
  只是需要所有者把关。

## 后果

- 批准时以**当时最新代码**发布，不冻结申请时刻的快照（工作区不是 git 仓库，做快照的成本与
  歧义都高于收益）；因此申请与批准之间若有会话在改代码，仍走既有 `chat_active` 确认闸门。
- 撤销共享 / 被共享者退出时，**该用户发起的**待审申请作废（置 `cancelled`），其他成员的申请
  不受影响；删除应用时全部申请随外键级联消失。
- 控制台没有通知中心：待审提醒靠应用卡片右上角角标，审批入口在卡片 ☰ 菜单的「共享管理」。
- 审批复用的表单形态来自商店安装申请（`release_application` 的 pending → approved/failed、
  审批人/理由/驳回留痕），但不共用表——应用发布与应用上架是两个生命周期。
