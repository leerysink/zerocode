# 提问卡与确认卡以消息流为唯一真源，不再靠挂起态与补发

问答结束后聊天框找不到问答内容，根因是两套真源：卡片由 `pendingAsk`/`pendingConfirm` 这类「挂起态」字段驱动，答完即清空、从不进消息流；模型在提问前那段说明文字只活在流式缓冲区，而工具轮不发收口事件，等下一轮收口时被直接抹掉（库里其实存了，所以刷新后又会回来）。决定把两张卡的真源改判为消息流自身的那对行——调用行给出题目、结果行给出答案，「有调用行无结果行」就是待答态、结果行到达即转只读留痕；同时让每个工具轮在进入工具调用前先把文字固化成消息，使实时流与刷新后的历史逐条同序。提问侧的挂起态字段删除。

**待答态不能只靠消息行重建**（本 ADR 初稿的错判，已回补）：工具行是在结果回来时才落库的，所以**待答的那次调用在历史里根本没有行**——assistant 行带着 `tool_args` 只能证明「有个调用没配对」，画不出题也画不出按钮。因此 hub 的提问卡补发恢复，`ask_user` 与 `confirm_request` 两个事件在找不到可附着的调用行时，由 reducer 合成一条无结果的调用行（args 事件自带），等价于实时流里先到的 `tool_call`。真源仍是消息流：补发只是把「这一行在等人」的事实重新说出来，事件本身不提供卡片内容。

确认卡另有**一处例外**，必须记下来：「本次调用需要确认」这个事实不在任何消息行里——它取决于写入确认开关与预览重启的运行时判据，前端无法从 `write_file` 的调用行推断它是在等确认、正在跑、还是已跑完。所以 `confirm_request` 事件从「卡片的数据源」降级为「标记哪一行在等确认」，卡片内容仍一律从消息行读。真源没有变，只是恢复待答态时多一次标记。

## 备选方案

- **新增专用事件与角色行**（`ask_answered` + 问答独立入库）：语义最清晰，但要改协议、改存储、改历史接口，且旧会话没有这些行，反而多出兼容分支。否决——现有两行已经承载了全部信息。
- **纯前端在提交时本地合成一条记录**：改动最小，但这条记录不在库里，刷新即消失，等于把「实时 ≠ 历史」的缺口挪了个位置。否决。
- **前端在执行态上加闸**（可交互 ⇔ 无结果行且 running）：不动后端，但孤儿行永远留在库里，靠 UI 遮着。否决——中断时由后端补写结果行，数据成对才是根因修法，且顺带保证回注模型时不缺 tool 消息。

## 后果

- `message_done` 的语义从「本次执行结束」扩展为「本轮输出收口」，一次执行会发多次。执行终态仍只由 `status` 事件判定，前端不得拿 `message_done` 复位 running。
- 按帧数硬断言的 WS 事件测试（`tests/test_ws.py`）需要跟着改，否则工具轮补发的收口事件会把计数打红。
- 卡片渲染从此必须同时认两种字段形状：实时事件的 `name/args/result` 与历史行的 `tool_name/tool_args/tool_result`。
- 卡片上的人话文案，判据是**刷新后能否重建**而不是字段来源：后端 `confirm_request` 带的 `summary` 不落消息行，但重连时 hub 会把同一份补发回来，所以待答态可以安全地用它；已答态没有补发、只能读消息行，文案就必须由前端按工具名生成。凡不可重建的字段都不得参与已答态渲染，否则实时与刷新后必然叉开。
- 确认的结果必须在库里留机器可读标记（`confirm: approved/denied/cancelled`），不能靠匹配「用户拒绝该修改」这类散文——需确认的工具各有各的拒绝文案。也不能复用裸 `cancelled`：中断补写的配对行同样是 `{cancelled: true}`，那条属于没派发的普通工具，拿它当确认结果会给 `read_file` 画出一张确认卡。
- 挂起点是内存态，进程重启（开发期改代码重启后端、崩溃）后卡片在前端仍停在可点状态，而 `confirm`/`ask_submit` 上行撞在空挂起点上什么也不会发生。为此新增 `interaction_expired` 下行：后端在「无挂起点且该会话不在跑」时回一帧，前端把待答行补成 `{cancelled: true}`（确认侧再带 `confirm: 'cancelled'`）并复位 running。仍在跑时不回——那多半是连点第二下，真实结果正在路上。
- 验收不变式：同一次执行，实时流渲染出的消息序列与刷新后历史渲染出的消息序列必须同构。
