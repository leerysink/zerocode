# 小程序分发边界与凭据治理

平台对小程序只做到「上传开发版 + 出预览码」，**不代提审、不代发布**：普通小程序没有提交审核与发布的公开 API，审核结果也不可控。凭据（AppID + 代码上传私钥）落在 `data/miniprogram_keys/{slug}/`（0600），不回显给前端、不进模型上下文；一个应用只绑一个小程序账号，AppID 全局唯一。

## 备选方案

- **自动设为体验版**：普通小程序没有这个 API；第三方平台才具备代操作能力，但那要求平台先取得第三方平台资质，成本与合规面都过大。
- **自动提交审核 / 自动发布**：同样没有普通账号的公开 API，且审核时长与结果不可控，与「最后一步由人决定」的诉求相悖。
- **凭据存数据库或应用源码**：数据库要新增加密与轮换；源码会让密钥进市场包与模型上下文，直接违反既有红线。
- **允许同一 AppID 绑多个应用**：开发版与预览码会互相覆盖，后台状态无法解释。

## 后果

- 用户在平台点完上传后，还要自己去微信官网完成**选体验版 → 提交审核 → 审核通过 → 发布**；平台只提供状态、预览码与步骤指引。
- 上传失败与发布**解耦**：旧开发版保留、发布结果不变、弹框可重试；平台重启导致的中断给固定提示。
- 绑定后跑一次**异步预检**（构建 + preview，不产生开发版），把私钥、IP 白名单、编译兼容性与 HTTPS 证书问题提前暴露；预检是唯一的早期闸门。
- 上传版本号跟随应用发布版本（`b<时间戳>`），描述带应用名与上传时间；上传闸门与 APK 一致，要求 `status_prod=running`。
- 平台只显示需要加白的域名与自身出网 IP；IP 白名单缺失、主体不一致、个人主体限制、2MB 主包限制等外部问题由用户在微信侧解决。
- 微信登录（静默 + 自动建号）与 AppSecret 注入应用 env 已对齐，但排在下一期，不在本条与本期范围。
