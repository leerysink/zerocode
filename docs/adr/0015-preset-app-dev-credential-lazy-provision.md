# 0015 预置应用的 dev 凭据在首次预览时惰性供给

ADR-0014 定下「凭据不进 init.sql」，于是 build-output 的预置应用只有 `workspace` / `app_project`
元数据行，没有 `app_config.dbcred.<slug>.dev`。而凭据原先**只在 `app_service.create_app` 里生成
一次，没有任何补建路径**：种子到另一台机器后点「预览」会拿到 409「请删除应用后重建」——在演示机上
等于预置应用全是死的，而照它说的重建会连刚上传的源码目录一起抹掉。我们决定：`engine.start_dev`
在读不到 dev 凭据时**现场**调 `provision_env` 建库建角色并登记（`_ensure_dev_cred`），取代 409 判死。

被否决的方案：保留 409（预置应用不可用，唯一出路是删除重建，代价是源码目录）；把凭据写进
init.sql（撞「凭据不入仓库」红线，且口令会随包分发给任何拿到包的人）；在 apply-init.sh 之后
加一步现场供给（要多一个服务器端脚本、每次发布都得跑，而实际只有首次需要，且那时凭据要先落盘
才能被 psql 用到，反而把口令写进了文件）。

## 后果

- 点「预览」从此**可能在平台库上执行 `CREATE ROLE` / `CREATE DATABASE`**——这个动作原先只发生在
  「新建应用」时。三道守卫，缺任一条都比继续跑更便宜：供给抛错 → 503（平台库连不上或连接账号无
  建库权限，属基础设施不可用，与 `db_admin` 的 503 口径一致）；供给结果缺 `db` 或口令 → 500
  （对齐 `create_app` 的同款守卫；空口令渲染进 `.env` 后，大型栈 compose 的 `${VAR:?}` 会在**文件
  解析期**拒收，报出来的是 compose 的英文错，比在这里早失败难懂得多）；**凭据健在时本函数根本
  不被调用**（调用方判空），所以存量库的口令永不被换掉，这条也是幂等的保证。
- 发布顺序被钉死：`prod.py` 硬要求 dev 凭据已在，否则 500「请先在预览环境启动一次再发布」
  （正式环境复用 dev 的凭据）。所以预置应用必须**先点一次预览、再点发布**，交付包的
  `README-deploy.md` §3 已如实写明。`prod` 侧不需要对称改动：它本就无条件 `provision_env`。
- 与 ADR-0014 的关系：ADR-0014 说「应用分库与凭据不进 init.sql，仍走平台既有机制」，本 ADR 就是对
  「既有机制」的补充——它原先只有 `create_app` 一个入口，现在多了「首次预览」这一个。两者不冲突：
  凭据始终由平台运行期生成、存在平台库里，从不进交付物。
- 供给是**惰性**的而非打包期的：打包全程不连数据库（共识之一），所以任何依赖数据库状态的东西
  都只能推迟到运行期。代价是「预置应用点第一次预览」比本地新建的应用多一步现场建库，日志里
  会多出「→ dev 凭据缺失，现场供给分库 `<slug>_dev`」一行——这是预期输出，不是异常。
