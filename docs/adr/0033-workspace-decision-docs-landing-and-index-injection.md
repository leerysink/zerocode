# 澄清结论落工作区 docs/，并以索引回灌给 Agent

需求澄清出来的决策与计划，落成**应用工作区里的文件**：`docs/adr/`（决策）与 `docs/specs/`（计划），
即磁盘上的 `apps/<slug>/docs/`。写入通道复用提问卡——Agent 先 `ask_user` 征询「要不要把计划写成文档」；免二次 `write_confirm` 的判定
只用两个**机器可判**的事实：本轮问过至少一道题（同意确实发生在提问卡里），且目标是 `docs/` 下的
**新建**文件。不去解析用户答的是「要」还是「不要」——那是散文匹配，真源在前端文案常量里，
改一个字就静默失效（ADR-0029 同类教训）；「不要」由模型自己遵守，而覆盖已有文档仍然要确认，
因为用户点头的范围是「新建这一份」。
文档写了没人读等于换个地方蒸发，所以每轮拼装时扫描这两个目录，把「文件名 + 标题 + 一句话摘要」
作为索引段注入 system 尾部（与 `<memories>` 同构的渐进披露），正文由 Agent 按需 `read_file`。
不采用「prompt 里提示模型自己去看 docs/」——那又是一条软指令，而软指令失效正是本次需求的起因。

`docs/` 判为**过程产物**，加入市场打包的 `EXCLUDE_TOP`。这里有个容易踩的默认语义：打包是**黑名单**制
（`app/store/packages.py` 的 `EXCLUDE_TOP = {deploy, sqlchange, app.json, README.md}`），
工作区新增的任何顶层目录会**默认被装进市场包**——不排除就等于公开，而 ADR 里可能含内部讨论。

**持久性必须说清，别误以为进了版本控制**：`apps/` 被 `.gitignore` 忽略，应用工作区目录里没有 `.git`，
它不是 git 仓库；而 `delete_app` 的 M1 裁定是只删平台记录、**不删磁盘工程目录**（`shutil.rmtree` 只存在于
建应用失败的回滚路径）。所以应用被删除后，`apps/<slug>/docs/` 留在磁盘上成为**孤儿目录**，
workspace 行已级联删掉会话与消息，平台再也召不回它。裁定是**接受**：文档随应用退出平台视野，
不做发布快照留存、不做删除前导出提醒——它本来就是这个应用开发过程的本地产物。

## 备选方案

- **只写 `memory_write` 的 decision 条目**：零新目录、已有跨会话召回。否决——用户看不见完整历史，也不是「doc 的 ADR」这个形状。
- **ADR 进记忆、计划进文件（两份都写）**：职责分开听着干净。否决——同一决策两份写法，不一致时没有真源。
- **正文全量注入 system**：确定生效。否决——十几个 ADR 就是几千 token 且每轮都付，成本随应用规模线性增长。
- **新增专用 `doc_write` 工具**：路径围栏天然、语义清晰。否决——多一条写入口要审计，还要新前端卡片渲染；`ask_user` 征询 + 受限免确认已经覆盖需求。
- **`docs/` 跟源码一起进市场包**：安装者能读到设计决策。否决——与 `README.md` 已被排除的既有裁定不一致，且包体积变大。
- **纳入 `releases/` 发布快照 / 删除应用时提醒导出**：让文档能对应版本或能被救回。否决——前者与「过程产物不进发布物」相反；后者要改 `delete_app`，跨了 M1「删除不做破坏性动作」那条线。

## 后果

- 应用契约的目录清单（`app/deploy/contract.py` 里那行只列了 frontend/backend/schema/sqlchange/deploy）必须补上 `docs/`，否则 Agent 不知道它存在。
- 通用工作区会话（`root_path` 由用户自填、没有 `app.json`）不注入应用契约，`docs/` 约定在那里**只能靠回灌索引**被看见——这是两类工作区的真实差异，不是遗漏。
- 索引注入需要条数上限与截断策略：只读 frontmatter 或首段，不读全文，否则扫描成本随文件数线性上升。
- 应用内 ADR 编号沿用 `NNNN-kebab.md`，写前先 `list_dir docs/adr` 取下一个序号——与 `sqlchange/D<日期>_<序号>` 同构的取号套路，不另发明规则。
- 模板不预置 `docs/`，目录由 Agent 首次写入时创建（避免给存量应用铺空目录，也让「有没有 ADR」成为真实信号）。
- 免二次确认这条分支一旦放宽路径围栏，就等于给 `write_file` 开了一个免确认通道；围栏判定要写成可单测的纯函数。
- 孤儿目录堆积是**既有问题**，`docs/` 不引入新故障（目录原本就因 `releases/` 而非空），只是让残留更有内容。
- **文档的写入时机裁定为「计划先行、决策可后补」**（2026-11-02 实跑复盘补的）。最初提示词只写「收口后问是否写文档」，
  没有时间锚点，模型自发把征询推到整轮最后——实跑序号：收口 53 → 连续 30+ 次代码写入 → 179 才问 → 182/194 落文档。
  它给的理由是在优化「打断次数」（`ask_user` 会挂起整轮），而不是遵循流程：这与规则 4 当初失效是同一种病，
  也是本 ADR 决定用门禁而不是纯指令的那个理由的再次印证。
  ADR 允许后补不是妥协：它记的「实际怎么定的、否决了什么」里确有动手后才成形的口径（字段命名、
  沿用项目现行 `V` 前缀还是照平台契约的 `D` 前缀），强行前置只会把结论写成猜测。两份文档共用一次征询，
  不为 ADR 再打断一轮。
