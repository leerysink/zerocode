# 0021 聊天页的「打开预览」走新标签，不内嵌 iframe

聊天页操作条上的「打开预览」一律 `window.open` 打开后端返回的 `preview_url`，**不做**站内抽屉 iframe、
也不做右栏内嵌 tab。预览未启动时该按钮禁用置灰并给 tooltip，不代为启动。

理由：预览的对象是**一个完整的应用**，而不是应用里的一段内容。本项目的应用可以是一整个 Win10 桌面模拟，
它需要的视口比聊天页能给的任何容器都大；iframe 里跑整栈还会带来跨域滚动、弹层、全屏类交互的一堆限制。
这与 ADR-0011 把内置文件管理器从弹框改成整页是同一条判断——「承载完整工作面的东西不该寄生在别的页面上」。
次要理由是地址栏：预览标签自己可刷新、可后退、可开第二个，这些能力不用我们再实现一套关闭态与 `nonce` 强刷。

「未启动就置灰」而非「点了顺手帮你启动」是刻意的：新标签先于栈就绪打开，用户看到的是一片连不上的白屏，
而在这个页面上他刚让 Agent 改完代码，白屏会被归因成代码错了。宁可让他多点一次启动。

被否决的方案：站内抽屉 + iframe（`AppsView` 已有同款可搬，但把整个应用压进依附在聊天页上的临时窗口，
且抽屉会盖住右栏）；右栏新增「预览」tab（300px 宽放不下一个应用）；点击先启动、轮询到 `running` 再自动
开标签（要等十几秒到一两分钟且中途无反馈，自动开标签还会被浏览器的 transient activation 拦掉）。

## 后果

- 预览地址只有后端一个来源：`list_apps` 每行的 `preview_url`，或 `GET /dev/status` 回体的 `url`。
  前端**不得**按 `dev_port` 自拼 `http://localhost:<port>`——部署基址是配置项，硬拼在容器化与远端访问下
  直接失效（既有红线，见 CONTEXT.md）。
- 主区因此只剩一个带文字按钮（启动/重启预览，文案随 `status_dev` 变身）加两个图标（打开预览、更多），
  避免与既有的「压缩上下文」「发送」「停止」抢一行宽度。
- `AppsView` 卡面的抽屉式预览继续存在，两种形态并存于同一产品：列表页是「评估这个应用」，就地看；
  聊天页是「验收我刚改的东西」，要全屏。这条分叉若将来要收敛，收敛方向是列表页也走新标签、删掉抽屉，
  而不是给聊天页补 iframe。
