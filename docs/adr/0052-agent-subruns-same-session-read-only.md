# 0052 子 agent 是同会话只读子 run：复用消息流，不开子会话、不给写面

- 状态：Accepted
- 日期：2026-11-18
- 规格：[docs/specs/2026-11-18-agent-subruns.md](../specs/2026-11-18-agent-subruns.md)
- 关联：ADR-0029（实时≡历史，子 run 的过程必须可回放）、ADR-0030（压缩水位，子 run 消息不进主历史）、
  ADR-0032（澄清门禁，子 run 不提问不写盘故不受门禁）、`docs/specs/2026-09-26-user-skills.md` §7
  （「subagent 化运行」一条被本 ADR 取代，仅那一条）

## 背景

用户要「主任务委派多个子 agent 并行干活」。现状是单会话严格单 run（`hub.running` 按会话占位、
`ws.py` 预占防双跑）、工具调用逐条串行，全库没有任何派生会话/子任务雏形。三条岔路互相纠缠：

- **载体**：每个子 agent 建子会话（`child chat_session`），还是留在同一会话里做成派生执行分支；
- **权限**：子 agent 是否拥有完整工具面（含写盘、写库、弹确认/提问卡）；
- **留存**：子 agent 的中间过程是逐事件实时下发并落库，还是只在结束时给合并回执。

## 决策

1. **载体 = 同会话子 run**。不新建 `chat_session`、不进会话列表；子 run 的每条消息落同一张
   `message` 表，用 `parent_tool_call_id`（委派那次调用的 id）与 `subrun_index` 两个可空列归属；
   事件走同一条 WS。理由：用户视野不分裂，会话列表/状态角标/5 秒轮询体系零改动；
   子会话方案下子 agent 里的提问/确认没有天然的人来答——要么只能做无交互子 agent，
   要么新增跨会话事件中继，收益不成比例。

2. **工具面 = 只读白名单**。子 run 只挂 `search / read_file / list_dir / db_query / db_schema /
   release_preflight / preview_status / preview_page`（应用类工具仍按「解析出唯一应用」才挂）；
   禁写盘、禁 `ask_user`、禁确认链类、禁 `browser_*` 走查、禁 `todo_write` / `memory_write`。
   落盘一律由主 run 走既有确认链（ADR-0027 的肌肉记忆不被稀释）。
   `browser_step` 能点击提交、会改 dev 应用状态（真写库），不满足只读语义，故整体排除。
   理由：并行写同一工作区需要文件锁或写入串行化，且 N 张确认卡轮流打断用户心流；
   只读保证并行无互踩。以后要放权只需改白名单，架构不动。

3. **委派形状**：一个 `delegate` 工具收一批任务书（`tasks: [{title, brief}]`），内部并发跑到
   全部落定，合并为一个 `tool_result` 回主 run——现有「工具逐条串行执行」的循环完全不动，
   并行度封装在工具内部。禁递归（子 run 工具面不含 `delegate`）；失败隔离（一个子 run 出错只影响
   自己那条回执，不取消其余）；上限可配：`subrun.max_tasks` 默认 5、`subrun.max_rounds` 默认 10
   （`<=0` 表示不限轮数，与主循环 `agent.max_tool_rounds` 同口径），均为账户级键；子 run 继承主 run 模型。上下文 = 主 agent 写的任务书 + 与主 run 同款的系统骨架
   （技能/记忆/决策索引照旧注入），**不含主会话聊天历史**——隔离彻底、成本可估。

4. **过程逐事件实时下发并落库**，满足 ADR-0029「实时≡历史」：子 run 的 assistant/tool 行与主 run
   同形落库（同一套凭据脱敏口径），实时事件与落库内容逐字一致。中途刷新时 `delegate` 的 tool 行
   尚未落库、历史重建不出卡片——这与「待答的 ask/confirm 在历史里没有行」同构，
   故由 hub 在 WS 连入时补发子 run 快照（状态在内存，随 run 收口丢弃）。
   子 run 的消息**不进**主 run 的模型历史与压缩水位。

5. **停止级联**：用户停止与所有在飞子 run 竞速取消（沿用 `_wait_or_cancel` 语义），
   委派那次调用按既有取消路径落一条 `{"cancelled": true}` 结果行；未收口的子 run 呈现为已中断。

## 备选方案

- **子会话载体**：白嫖现有 WS/hub/run 全套、并行零成本成立；但用户视野分裂，且子 agent 的
  提问/确认没有天然的人来答，必须加跨会话中继或砍掉交互——两个代价都不小。被否决。
- **全工具面 + 确认卡回流**：能力最完整；但 hub 挂起结构要按 run 归属、用户被 N 张并发确认卡
  轮流打断、并行写同一工作区需文件锁。被否决，白名单留作以后扩。
- **即发即忘、事后收结果**：最灵活；但主 run 多一种挂起语义、事件时序更复杂，首版不做。
- **允许递归委派**：树深、成本、停止级联、事件嵌套全部递归化，首版不做。
- **子 run 降档模型**：省钱但要引入第二个模型回落链，首版继承主 run 模型。

## 后果

- **`add_message` 需要并发护**：`seq` 由 `max(seq)+1` 现算，多个子 run 并发写同一会话会撞
  `ux_message_session_seq`。以进程内 per-session 锁串行化写入（与 hub 内存态同一单进程假定）。
- **并行成本**：一次委派最坏 5×10 轮 + 工具调用，token 消耗数倍于串行；上限由 `subrun.*` 封顶，
  不做全局并发闸（平台现状本就无全局并发控制）。
- **user-skills 规格 §7 的「subagent 化运行不做」一条被本票取代**（仅那一条；技能的安装、
  受控读面等其余结论不变）。
- **子 run 生命周期随主 run**：进程重启不恢复（与 run 语义一致），不落常驻状态表。
