# 0069 关闭自助注册，改邀请码发号；首号空库自举

- 状态：Accepted
- 日期：2026-11-23
- 关联：ADR-0003（**取代**其「实例内开放注册」这一半运行假设，owner 隔离与 actor 登录主体不变）、ADR-0067、CONTEXT「邀请码」「首号自举」

## 背景

管理员要有封禁能力。但注册端点完全敲开、只要求昵称唯一，被封者换个昵称十秒就能回来，
封禁形同限速不封路。拷问阶段裁定：封禁要有效，入口就得受控。

## 决策

1. **入口收口为邀请码**：管理员签发一次性码，使用者自己去注册页输码、自己定昵称与口令。
   「管理员直接建号并设初始口令」被否——口令经他人之手，且平台**至今没有任何改口令路径**
   （无端点无 UI），发出去的口令永远收不回；补改口令又要连带吊销旧会话，复杂度追平邀请码。
2. **首号空库自举**：`actor` 表无任何账号时注册照常放行且免码，一旦有号即关门。
   这样 `SELECT NOT EXISTS (SELECT 1 FROM actor)` 那条首注册当选创始人、承接无主存量、
   划归 `llm.*` 的事务原样保留，新机器开箱与现有部署脚本零改动。
3. **复用注册事务而非另建激活流**：昵称唯一约束、bcrypt、会话签发都走现成的 `register`，
   邀请码只是它前面的一道闸。

## 备选方案

保留敞开注册只做账号级封禁（封禁无牙）、首号走 CLI/环境变量初始化（Web 面最干净，但注册事务
里的存量承接逻辑要搬家、部署多一步人工）、注册需管理员逐个批准（多一套 pending 审批队列）——均被否。

## 后果

- 登录页出现「邀请码」字段，`/register` 从公共入口变成凭证入口；`GET /api/users` 全平台花名册
  对任一登录账号可读这条现状不变（它不泄露归属，只是名单）。
- 封禁从此有牙，但代价是**自用场景变麻烦**：创始人自己想多开几个号也得先签码。
- 邀请码是新的高价值凭据：泄露等于开放注册。需要作废通道，且不该进日志。
