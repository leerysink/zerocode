# 0020 聊天页应用操作条按页挂载现成弹框，不抽公共 AppActions 层

聊天页底部新增的应用操作条（启动/重启预览、打开预览、更多）**不新做任何查看类界面**：预览日志、资源监控、
发布记录、去发布四项直接挂载应用列表页已有的 `DeployLogPanel` / `MetricsModal` / `PublishHistory` /
`PublishModal`，壳子也沿用各组件在 `AppsView` 里的原样（日志侧边抽屉、其余居中 `a-modal`）。同时**刻意不抽**
一个跨页共享的「应用操作」组件或注册表，两处各挂一份。

理由：这四个组件的 props 契约本来就只是 `app` 对象（或 `appId` + `active`），没有一处依赖列表页的上下文，
搬过来零改造；而抽公共层要先回答「一个组件同时服务卡片和输入框工具条，尺寸/触发/关闭态听谁的」，
这个问题在当前只有两个消费方时没有好答案，只会产出一个为抽象而抽象的壳。更关键的是**行为一致性靠复用
组件本身保证已经足够**——需要一致的是「点发布弹出的是同一个表单、同一套破坏性确认」，而不是「两处用同一个
挂载代码」。

文案分叉是这笔交易的代价，且是**有意的**：同一个 `POST /dev/reset` 在卡面叫「重建 dev」、在聊天页叫
「重建 dev 库」。前者紧邻一堆应用管理动作，语境里 dev 就是那套栈；后者紧邻「重启预览」，差一个字就会被
读成「重启得久一点」，而它实际做的是 DROP 并重建 `<slug>_dev`。宁可在两处各起一个贴合上下文的名字，
也不为了字面统一让聊天页那个入口误导人。

被否决的方案：抽 `<AppActions>` 共享组件（两个消费方的布局差异要先设计一套 slot 协议，成本大于收益）；
统一一个右侧大抽屉装下所有查看类内容（`PublishModal` 是带破坏性确认的表单流程，塞进抽屉削弱仪式感，
且抽屉会盖住右栏文件面板）；把日志塞进右栏当第 4 个 tab（`FilePanel` 只有 300px 宽，日志行压得没法读）。

## 后果

- 四个弹框在聊天页**互斥**：同时只开一个，开新的即关旧的；切换会话时全部关闭。旧弹框挂着上一个应用的
  `app.id` 是事故源（点「发布」会发到错的库），这条规则不许放宽成「组件自己处理」。
- 聊天页拿不到 `app.id`（只有 `currentWorkspaceId`），反查靠 `GET /api/apps` 一次调用按 `workspace_id`
  匹配。该接口已按 `owner_user_id` 过滤，所以**反查不到即整组隐藏**，一个判据同时覆盖未绑定工作区、
  无应用、非本人应用三种情形；前端不再重复实现 owner 判定，也就不存在与后端漂移。
- 预览状态走轮询 `GET /dev/status`（页面可见时 5s、`starting` 期间 2s），**不订阅** `/ws/deploy/{id}`。
  聊天页已有一条 `/ws/chat/{sessionId}`，再挂一条常驻 WS 要处理重连与切会话换订阅；`DeployLogPanel`
  与 `PublishModal` 内部各自的 WS 属于「弹框开着才存在」的短连接，不在此约束内。
- 「重建 dev 库」确认后**自动弹开预览日志**：它的结果只走 WS `dev_reset_result`，而本页按上一条不订阅 WS，
  自动打开日志面板是让用户看到 `drop → provision → fold sqlchange` 实进的唯一低成本通道。
- 两处文案不再逐字一致，改 `resetDev` 的确认文案时要同时记得 `AppsView.vue` 与聊天页操作条两个调用点。
