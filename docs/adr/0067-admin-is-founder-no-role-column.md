# 0067 平台管理员复用 actor.is_founder，不引入 role 列

- 状态：Accepted
- 日期：2026-11-23
- 关联：ADR-0003（actor 升级为登录用户）、ADR-0050（审批权收口创始人）、CONTEXT「创始人」「管理员」「子账号」

## 背景

平台要从「各人自玩」走向有运营方的多租户：需要有人封禁账号、按账号限额、下发默认配置。
现状 `actor` 只有一个特权位 `is_founder`，它同时承担两重语义——注册事务里「承接全部无主存量
的那一位」，以及治理面上「商店唯一审批人 + 四个只读面 bypass owner 过滤看全员数据」。
拷问阶段先定了「子账号」不是父子归属，平台是单层治理：管理员一方，其余账号彼此平级。

## 决策

**管理员身份 = `actor.is_founder`，不加 `role` 也不加 `is_admin`。** 第一个注册的账号天然
就是平台管理员，治理面直接沿用既有 founder 判定，不新建第二套特权位。

## 备选方案

- **新增 `role`（admin/member）并迁移全部 founder 判定** —— 管理员可转移、可增员，与
  「谁先注册」解耦。被否：本期只有一位管理员，为不存在的需求付一次 schema 迁移加 8+ 处判定改造。
- **新增 `is_admin` 与 `is_founder` 并存** —— 改动最小。被否：出现「是 founder 但不是 admin」
  的空语义组合，商店审批用 founder、治理面用 admin，日后必须再合并一次。

## 后果

- **管理员不可移交、不可增员**。这是本决策买下的约束：若将来要换人或设多位管理员，得先补上
  `role` 列并回答「承接存量的是 A、治理的是 B」这种分裂状态——那时 ADR-0003 的注册事务语义
  要一并重审。
- 「承接无主存量」与「有平台治理权」永久绑定在同一行上。读代码时 `is_founder` 两处含义都成立，
  不拆分；新增治理端点一律复用 `_require_founder` 这一族判定，不另造门禁 helper。
