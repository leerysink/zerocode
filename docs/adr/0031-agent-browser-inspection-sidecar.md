# Agent 浏览器验证跑在独立 sidecar，而不是后端容器内

平台 Agent 新增「预览页浏览器验证」时，headless 浏览器渲染的是用户应用页面，页面 JS 属于不可信内容。后端容器持有 docker.sock 与平台库凭据，把 Chromium 放进后端容器等于把「页面被攻破」升级成「宿主 root」；因此浏览器服务独立成 sidecar 容器：无 docker.sock、无平台库凭据、非 root、限资源，后端只经内部 HTTP 调用它，它只经 host-gateway 访回应用 dev 端口。被否决的备选：后端容器内进程（接线最简单，但 Docker 内 Chromium 通常只能关沙箱，爆炸半径不可接受）与宿主独立服务（交付包无法自动管理，部署多一套手工依赖）。

## 后果

- 对外只暴露一个只读工具 `preview_page`：浏览器只能读当前会话所属应用的 dev 预览页，不接收任意 URL；应用身份仍由后端从 `chat_session.workspace_id` 解析后传入，模型无法指定其他应用。
- sidecar 只解决「隔离运行环境」，不解决所有网络风险：它仍能访问宿主已发布端口与公网，残余风险按「用户自己的页面被看了」评估，不按平台凭据泄露评估。
- 交付物多一个 compose 服务与镜像（官方 Playwright 镜像或等价精简镜像），build-output 与部署检查清单需要同步；这是隔离换来的固定成本。
