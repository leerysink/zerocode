# 0049 应用共享：单角色「被共享者」+ 聊天取只读旁观，不做多人共聊

平台应用长期是单所有者模型：`app_project.owner_user_id` 是唯一归属，列表/详情/预览/聊天/发布
全部按当前账号过滤（`app_service.list_apps/get_app` 的 owner 判据，别人的应用一律 404）。
本次要给应用加共享能力，本 ADR 定两件会锁死后续形态的事：

1. **权限模型只有一个角色**：被共享者。所有被共享者拿同一套固定权限（查看信息、dev 预览启停/重启
   与日志、只读旁观聊天、观测只读、工程文件只读、DB 只读查询、prod 启停、移动端弹框查看与 APK 重打；
   删除/重命名/回滚/上架商店/小程序上传/DB 写/迁移执行/重建 dev 库/文件编辑仍仅所有者）。
   不逐人勾选能力——判权只留一个函数，测试面不随共享人数增长。
2. **聊天是只读旁观，不是多人共聊，也不是各聊各的**：被共享者能看所有者会话的历史与实时运行，
   但不能发言、不能回答提问/确认、不能停止执行。

## 备选方案

- **同一批会话多人共聊**（所有成员看同一会话列表、接同一会话继续聊）：最像「共享聊天框」的字面形态。
  否决理由是 hub 与 `chat_session` 按单用户设计：一个 run 串行执行、`ask_user`/`confirm_request`
  只能有一个人回答、取消没有发起人归属。多人共聊要新增消息发言人列、待答归属、同工作区任务串行，
  等于重做 Agent 交互层，爆炸半径远超本次共享需求。
- **各聊各的独立会话**（被共享者在同一工作区建自己的会话）：实现最省（只需换判权），但 Agent 会
  直接改共享工程文件，等于把「可改生产代码」交给被共享者，与「删除不可、发布需审」的克制目标自相矛盾。
- **完全不给聊天，只给预览**：最保守。否决理由是所有者排查问题时需要被共享者能看到上下文，
  只读旁观正是「能看不能动」的最小形态。

## 后果

- 被共享者不能借聊天驱动 Agent 改代码；将来若要做协作编码，需要新的 ADR 重定义消息归属与执行并发。
- 只读旁观复用现有消息流与历史接口，改动集中在两处：WS 订阅的只读鉴权、前端隐藏输入区与
  提问/确认/停止按钮。
- 撤销共享立即生效，包括正在进行的实时旁观；共享关系不可转授。
