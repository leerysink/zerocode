# 压缩留痕走读取侧投影，压缩开始帧由压缩服务单点下发

「压缩上下文」过去只在跑完之后由前端在内存里 push 一条提示条：点击时聊天流毫无反应（只有按钮转圈），自动压缩更没有开始帧，而这条提示既不落库也不投影——刷新或切回会话就查无此事，用户无法判断这段历史究竟被压缩过没有。决定：压缩确定要执行后（skip 判定之后）由 `compaction_service.compact` 单点下发 `compacting` 起始帧，手动与自动两条触发路径共用；前端据此在聊天流里放一枚「未定稿标记」，终态（完成/skip）就地换成定稿记录而不是再追一条，本轮终态（error/status/interaction_expired）则摘掉未定稿标记，不留转圈残块。落库侧不改：刷新后的留痕由 `GET /sessions/{id}/messages` 读 `compaction` 表投成 `role=notice, kind=compacted` 的合成行，插在水位那条消息之后；文案只在前端按 `kind` 定义一份。

## 备选方案

- **压缩时往 `message` 表写一行 notice**：一次写入终身可见，无需投影代码。但 `compaction_service.rows_after` 与 `loop._history` 都读这张表，提示条会被当成对话内容喂给模型并被计入压缩估算字数，得在两处按角色排除；而「哪条消息之前被摘要覆盖」本来就有 `compaction` 表做权威记录，多写一行是第二份真相。否决。
- **只改实时显示，不管刷新后**：改动最小，但自动压缩多半跑在长回合中间，用户刷完页面只看到回答、看不到压缩痕迹，等于问题只解决了一半。否决。
- **`compacting` 仍由 ws 端点发、自动压缩另发一帧**：两处发同一语义的帧，skip 分支还要反过来补收帧——正是过去自动压缩没有开始帧的原因。否决。
- **历史接口直接回后端硬编码文案**：省掉 `kind` 字段，但同一句话在前端常量与后端字符串里各存一份，改一处另一处对不上。否决。

## 后果

- 留痕与摘要同源（`compaction` 表），压缩失败或 skip 不产生任何持久行，无需清理。
- `GET /messages` 多一次 `compaction` 查询，并在返回数组里插入非 `message` 行：`id` 为 `null`、`seq` 复用水位值。渲染按数组顺序（`v-for` 用下标作 key），不认 `id`；新增按 `id` 消费该接口的代码要排除合成行。
- 前端 `store.messages` 里的压缩标记是活对象，靠 `splice` 原地替换而非改字段，避免裸对象绕过响应式代理。
- 自动压缩期间不再本地拦截发言：那一刻 `running` 已为真，插话本该交给后端队列；本地只在纯手动压缩（会话空闲）时把话拦在输入框。
- 刷新恰好撞上压缩进行中时，未定稿标记与按钮 loading 一起消失（后端不重放 `compacting`）；定稿提示仍会到达，下次打开由投影补齐——留痕的最终一致性优先于进度连续性。
- 验收不变式：手动与自动压缩都先出现 `compacting` 再出现 `compaction_done`；skip 只出现 `notice`；同一会话连续两次压缩在历史接口里出现两条 `kind=compacted` 行且都排在各自水位之后；模型请求的消息里不出现「已压缩上下文」。
