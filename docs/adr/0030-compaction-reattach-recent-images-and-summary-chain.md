# 压缩后重挂最近带图消息，摘要改为链式合并

聊天图片输入上线后，压缩水位与「只保留最近 8 条原文」的口径会把带图消息很快推出模型历史：一次工具密集的回合就能让它越过保留窗口，摘要里只剩文件名，模型再被追问时只能回答「看不到图片」。同时，压缩摘要每次只把上一次水位之后的消息送去摘要，系统又只注入最新一条摘要——第二次压缩后，最早那份摘要（可能正是图片存在过的唯一记录）被静默丢掉。决定：压缩水位照常前进；每次组装模型历史时，把历史窗口（`agent.history_window`，默认 40 条）内最近 2 条带图 user 消息按原文重挂回上下文，图片字节沿用现有 10MB 内联预算；更早的图仍只保留摘要记录。摘要改为链式：新摘要以上一份摘要为输入，保证最新摘要覆盖全部已压缩历史，并封顶 8000 字符；摘要必须保留带图消息序号与文件名，系统提示词明确「只有文件名、没有 image_url 的图不可查看，不要假装看过，请用户重发」。

## 备选方案

- **水位停在带图消息之前**（图片消息不进摘要、原文保留）：语义最直观，但一张旧图会让水位长期卡住，后文持续膨胀，压缩反复触发却清不掉；需要额外的「释放」规则才可用。否决。
- **把重挂条数与窗口做成配置项**：更灵活，但多两个配置面与设置页说明，而现有「最近 2 条带图消息内联」本身就是硬编码契约。本期先与现有窗口对齐，不新增配置。否决。
- **注入时拼接所有历史摘要**：不改摘要器，但 system 上下文随压缩次数线性增长，还要淘汰策略。链式摘要让始终只有一条有上限的最新摘要。否决。
- **维持纯文本摘要、只改提示词**：改动最小，但用户仍然看不了刚发过的图，等于把问题转述给用户。否决。
- **任意历史图可重看（按附件 ID 重新读取）**：能力最完整，但 OpenAI 兼容端的 tool 消息无法承载图片 part，需要新的消息注入协议与预算规则。留作后续能力，不在本次范围。

## 后果

- 压缩水位语义不变：重挂不阻止水位前进，模型上下文保持有界。
- 重挂消息与摘要可能轻微重复（摘要提到图片存在，原消息又出现一次），接受。
- 摘要链改变 `compaction` 表的语义：每条新摘要覆盖全部已压缩历史，旧行仅作审计与回滚，不再依赖逐条增量拼接。
- 模型可查看的旧图范围仍是「历史窗口内最近 2 条带图消息」，不等于历史图片任意复用。
- 验收不变式：压缩后，最近 2 条带图 user 消息的模型请求里必须出现 `image_url`；第 3 条及更早只能出现文件名占位；连续两次压缩后，第一份摘要中的任务目标与图片记录仍出现在最新摘要里。
