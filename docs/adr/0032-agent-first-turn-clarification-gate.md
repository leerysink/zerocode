# Agent 首轮澄清门禁：写文件前硬性要求需求对齐

平台 Agent 的系统提示词里早就有「需求含糊就用 `ask_user` 提问」这条规则，但它是软约束——
模型经常不遵守，拿到一句话需求就直接开工，产出与用户预期偏差大、返工多。
决定把「新任务开工前必须完成需求澄清」从指令层升级为**代码门禁**：
`loop` 在放行第一批 `write_file`/`edit_file` 前检查两个信号是否都成立——本轮消息流里至少有一次
`ask_user` 且已有结果行（用户回答或点「自行决定」），并且模型显式调用过 `clarify_done` 声明对齐完成；
两者缺一即挡回工具调用，返回引导文本让模型先发起提问。同一任务内两个信号齐了之后不再拦。

`clarify_done` 允许模型声明「需求已明确，无需提问」来跳过 `ask_user`，这是给「把标题改成 X」
这类一句话小任务留的逃生口。但豁免必须**可审计**：`clarify_done` 必传一个字段回显「我对需求的理解是…」，
跳过提问时这行理解要渲染进聊天消息流，让用户一眼看到 Agent 理解成了什么、并能在下一条消息里一句话纠偏。
豁免的判定权留在模型侧，代价是它可能滥用；把豁免从隐形变成可见是本决策的第二根支柱。

**拷问流程的形态是两段式**：Agent 先输出一段结构化解读（需求分层翻译 / 歧义词候选含义枚举 / 动机推测），
并用一张提问卡请用户确认「解读有无偏差」——**这张解读确认计算作第 1 题**；确认后才逐条单题推进。
细则全部写进 `build_system_prompt` 的新增段落，而不是放进技能目录：技能是账户级、用户可删可改的存储，
平台默认能力住在那里会出现「用户删掉了自己的拷问流程，然后抱怨 Agent 不问问题」。

**提问预算是软目标**：prompt 写「通常 3~5 题应收口」，但**不设硬上限**。硬上限的失败模式已经想过——
后端拒绝第 N 次 `ask_user`，模型会改用纯文字提问绕过工具，提问卡统计失真、用户还得自己打字回答，比不加还糟。
取而代之是一道方向正确的止损：同一个任务内第 6 次 `ask_user` 时，后端在回注消息里插入一条提醒
（「停止追问，按最合理默认开工并声明假设」），**提醒而不拒绝调用**。阈值 6 进配置项，可调。

## 备选方案

- **只加强 prompt 指令**：改动最小，但规则 4 已经是加强过的指令，用户痛点正是它不生效。否决——软约束已被证伪一次。
- **单信号（只看 `ask_user` 留痕）**：零新工具、判定确定，但「问了一句废话」也能过闸，问了不等于问到位。否决。
- **单信号（只看 `clarify_done` 标记）**：语义表达的是结论而不是动作，但完全不需要用户配合，绕过成本比 ask_user 更低。否决。
- **全程门禁**（每次写文件都检查）：最严格，但一句话改错字、续做上一步任务都要被挡，把体验做差。否决——只在任务首轮生效。
- **门禁触发时由后端直接弹一张「跳过澄清？」确认卡**：用户第一次被挡就能一键根治，不用等模型先编一道题才有按钮可点。否决（本次）——新增一种卡片形态，按 ADR-0029「实时≡历史」它必须能进消息流重建，前端成本明显大于复用现有提问卡；若实测摩擦过大可重新评估。
- **后端按任务类型白名单决定可否豁免**：分类器写不准（「改标题」可能连带改十几个文件），误判会把门禁开成漏的。否决。

## 后果

- 门禁挡的是 `write_file`/`edit_file` 这类写动作，只读工具（`read_file`/`list_dir`/`db_query`）与 `ask_user`、`clarify_done` 自身不受影响——否则模型无法在门禁内完成澄清。
- 「本轮」以**最近一条用户消息**为界：用户每次输入都算一次新任务尝试，门禁重新起算。因此「自行决定」按钮的语义要从「本题放弃」扩展为「本题放弃 + 本会话不再强制澄清」，否则用户点完仍会被下一轮再挡一次。这是既有术语的语义变更，`CONTEXT.md` 的「问答与确认交互」一节要同步。
- `clarify_done` 是新的用户可见留痕，不只是控制位：它进消息流就必须能被历史重建，不能只发事件（ADR-0029 的不变式在这里同样适用）。
- 前端要新增一类「Agent 认为需求已明确，直接开工」的可见标注，与提问卡共用消息流真源。
- 需要为「门禁拦下 → 模型转而 ask_user → 用户回答 → 放行」和「声明无需澄清 → 回显理解 → 放行」两条路径补 pytest；FakeLLM 的桩要同步新工具的签名，否则 `test_ws.py` 会静默挂死（既有踩坑）。
