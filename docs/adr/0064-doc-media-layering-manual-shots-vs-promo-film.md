# 0064 文档媒体资产分层：手册浅色静态图进普通 blob，宣传短片不进仓

- 状态：Accepted（2026-11-21 改写第 4 条：原「成片进仓 + 配 git-lfs」被 Gitee 无 LFS 推翻）
- 日期：2026-11-20
- 关联：ADR-0055（控制台主题统一）、ADR-0058（登录页固定深色豁免换肤）、
  ADR-0062（控制台四页统一）、CONTEXT「操作手册」「宣传短片」「本机补美」

## 背景

手册 `docs/user-manual.md` 20 章只有 12 张配图，其中 8 个章节零图（第 2、6.1–6.3、7、8、9、
11、16、18 章），另有 4 张是 11-03 那代、早于 11-19~11-20 的两轮界面重构，与手册第 9 行
「已逐张对照当前代码核对」的声明不符。补图只能从演示站 `159.75.185.70:8100` 取：线上 CSS
里已含 `.zc-panel`（`7f20a6c`，2026-11-20 15:20 引入），它是唯一「代码 = master、数据 = 真实」
的界面来源，本机空库拍不出有内容的应用页与商店页。

同时要为平台做一条对外介绍视频。仓库当时 `.git` 只有 17M，一条 1080p 成片的体积与之同量级——
二进制一旦进 git 历史就永久占位，删不掉，所以第一版把它设计成走 git-lfs。

## 决策

1. **手册补图口径定为「广度 + 表现力」**：零配图章节全部补图，关键章节用**交互态分步图**
   （弹框已打开、☰ 菜单已展开、查询已出结果）。第 19 章 FAQ 与第 20 章端口约定**刻意不配图**
   ——纯文字更合适。执行结果：新增 16 张，既有 12 张引用**全部**在当前界面重拍（原估只 3 张受影响，
   `git log --since=2026-11-16` 证明 ChatMessages/AskUserCard/DiffBlock/MobileModal 等都动过），
   手册引用数 12 → 28。
2. **演示站操作边界收在「只读 + 可逆预览」**：允许导航、展开已有内容、启停应用 dev 预览栈
   （停了即归零）；**禁止**发布、回滚、删除与写库。因此凡是需要真跑一次才存在的界面，
   不在演示站上拍。
3. **媒体主题分层，不做全局换肤**：手册配图一律浅色（与读者默认看到的界面一致），
   暗色只用于宣传短片。手册不因片子而重拍成深色。
4. **成片不进仓库，以文件形式另发**（2026-11-21 改判，取代原「进仓 + 只给视频配 LFS」）：
   Gitee 主仓不提供 LFS，含 LFS 对象的提交在批量协商阶段就被整条拒掉；改回普通二进制则要把
   8~9MB 永久焊进历史。两害相权，短片不进 git，README 与手册**不留指向仓库内媒体的链接**（宁可
   不写，也不留死链）。`.gitattributes` 因此**不加** `*.mp4` / `*.webm` 的 LFS 规则——留着只会在
   别人提交媒体时制造一条看起来像鉴权故障的失败。
5. **生成镜头优先在演示站上找零写入的等价态，实在没有才动用「本机补美」**：宣传片主体镜头
   来自演示站已有历史会话（真实数据、只读）；打字机镜头用「在输入框敲字但不点发送」拿到，
   发布进度弹框拍它的**受理前态**（底部才是「立即发布」，受理链只在 `autoStart && mode==='rollback'`
   才自动触发）。**执行记录（2026-11-20）：本机补美一次都没用上**——原先为它准备的本机 dev 栈
   与模型凭据没用出去，少维护一套环境。

## 备选方案

- **成片进仓 + 只给视频配 LFS**（本 ADR 的第一版决策）：物料与手册同源、clone 即得。
  **实测被否**：Gitee 免费版不提供 LFS，这条路径在 push 阶段是死墙，不是配置问题。
- **成片改回普通二进制进仓**：一次推成，不依赖任何账号动作；代价是两版片子约 17MB 永久留在历史里，
  `.git` 从 38M 涨到约 55M，且以后每改一次片子就多焊一块。用户选择不要这条路。
- **压到 720p / 5MB 以内进仓**：历史代价减半；代价是字幕与小字控件糊，且仍需重写本地三笔提交
  （会连带改到并行会话那笔的 hash）。被否。
- **手册整体改深色以求与片子同调**：观感最统一；代价是既有 12 张浅色图全部重拍，镜头总量从约 20
  涨到约 32，且深色截图嵌在浅色页面上边缘突兀。被否。
- **为拿最真实界面在演示站上真点一次发布**：界面无可争议；但那台机 3.5G 内存，构建期间全站变慢，
  库里会多一条真实发布记录，失败还会卡住该应用的发布闸门。被否。

## 后果

- 主仓在 Gitee，而 `leerys/zerocode` 不是付费/试用企业仓——**Gitee 压根不提供 LFS**，不是配额问题。
  含 LFS 对象的 push 卡在上传前的批量协商：`lfs batch error: LFA auth batch error: LFS only
  supported repository in paid or trial enterprise`，整条 push 不走、远端一动不动（措辞容易被误读成
  鉴权失效而去重试登录）。普通 blob 照推，只有被 LFS 追踪的那几项是墙。GitHub 侧是每 15 分钟从
  Gitee 单向拉取的镜像，从下游往上游写会被下一次拉取覆盖，不能拿来绕。被明确否掉的绕法是
  `GIT_LFS_SKIP_PUSH=1` 硬推：远端只留 131 字节指针，等于把已知坏状态推上去。
- 「把媒体从已提交的历史里摘出来」不是加一笔删除提交就能了事的：只要**推送区间内**任何一笔提交
  引用过 LFS 对象，pre-push 就会去协商那些对象，照样被拒。所以短片不进仓必须**重写本地那几笔未推送的
  提交**，而重写会连带改写区间内他人提交的 hash——本次是并行会话的 `c75f93b`（内容不变）。
- 片子作为文件交付，位置在 `.scratch/video-20261120/zerocode-intro/final/zerocode-intro.mp4`
  （88.25s / 1920×1080 / H.264 + AAC / 中文旁白 + 21 条整句字幕 + 轻 BGM）。它没有公开地址，
  README 与手册里因此没有短片入口；等定了托管（外链 / 企业 LFS / 二进制进仓）再把链接补回去。
- `tests/test_promo_media.py` 保留：它写的是这条片子的验收口径（时长预算、画幅、音轨、非 LFS 指针），
  在片子进仓之前恒为 skip——这是有意的，别把它当失效测试删掉。
- 手册配图与视频是**同一次演示站行程的两个产物**：截图阶段若改了演示站主题或启停了预览栈，
  必须复位后再拍下一张，否则浅色口径会被自己拍脏；登录态是同账号单会话，脚本登录会把
  浏览器上的 `tsadmin` 顶下线，两边不能并行。
  **这条复位有个反噬（2026-11-21 踩实）**：录屏引擎只要 `.auth-state.json` 还在就不重跑 login，
  于是「为手册把账号切回浅色」之后，整片 console 镜头都拍成了浅色——主题口径不是靠录制脚本里的
  `login()` 保证的，而是被缓存的登录态说了算。正确顺序是：先拍完浅色手册图，再重建暗色登录态录片，
  最后才复位浅色。
