# 0046 run_check 用平台写死的 preset，红线改写为「无通用命令执行面」

Agent 需要在一个回合内自己发现类型/编译错误并在回合内修掉（ADR-0036 已把类型正确性定位为
「AI 自查 + 预览走查」，而非构建期闸门），但平台现行红线是「工具面没有任何 shell/命令入口」，
由 `tests/test_preview_tools.py::test_no_command_execution_tool_exists` 逐字钉住工具名单与禁用名。
我们决定新增 `run_check`：检查项（preset）由平台代码写死，模型只能选 preset 名、不能传任何命令、
参数或路径；执行载体是一次性容器（`docker compose run --rm --no-deps <service> <写死的 argv>`，
与 `sqlrun` 的迁移容器同构）；结果只作报告，不阻断发布、不写任何状态。同时把红线改写成
**「工具面无通用命令执行能力；只允许平台写死的 preset」**，并同步修订那条测试。

## 备选方案

- **暴露 run_command/run_shell**（任意 argv）：能一劳永逸解决所有自检需求，但它把平台其余全部围栏
  一起作废——shell 可以 `cat deploy/.env`（绕过 M-3 凭据读禁）、`rm -rf`（绕过写保护与确认卡）、
  `curl` 外发用户代码。红线保护的从来不是「执行能力」本身，而是这些围栏的可绕过性。
- **复用 dev 栈容器 exec**：省一次冷启动，但要求预览已经在跑；而「预览起不来」恰是最需要自检的时刻，
  且它同样是命令执行面，却没换来任何隔离收益。
- **检查结果作为发布闸门**：ADR-0036 已否决过同一形态——把 AI 生成代码的类型噪声变成用户非修不可的
  发布门槛，闸门只会逼人反复点重试。

## 后果

- 新增一个检查项必须改平台代码并随包发布，不能由配置或用户输入扩展。这是刻意代价：可扩展的命令面
  等同于通用 shell。
- 每次 `run_check` 都是冷启动容器，几十秒起步；后端 `mvn compile` 依赖 per-app `.m2` 卷，首次更慢。
  因此它适合「改完一段后自查」，不适合每轮都跑。
- 红线测试的语义从「名字黑名单」变为「preset 白名单 + 未知检查项拒绝」，新增工具时仍必须同时更新
  该测试与注册表，防漂移的强度不低于从前。
