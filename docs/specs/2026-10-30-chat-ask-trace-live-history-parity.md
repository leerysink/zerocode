# 聊天框问答留痕与「实时 ≡ 历史」同构

- 日期：2026-10-30
- 术语依据：`CONTEXT.md` §问答交互（ask）
- 决策依据：`docs/adr/0029-chat-cards-sourced-from-message-stream.md`

## 1. 问题陈述

一次问答（`ask_user` **提问卡**）答完之后，问答记录从聊天框里消失了：卡片本身被清空，只剩一个折叠的原始 JSON `🔧 ask_user` 工具块；模型在提问前说的那段说明文字也一并没了。但刷新页面后这些内容又全部回来——因为库里其实都存着。

这说明实时流与持久化历史走的是**两套渲染路径**，缺口有三处：

1. **问答无留痕**：`ask_user` 事件只写挂起态字段 `pendingAsk`，从不进消息流；提交/自行决定后卡片直接置空。问题与用户的实际回答都不在消息流里。
2. **中间文本被抹掉**：模型在工具轮里流式输出的说明文字只活在 `streamingContent`；后端在有 `tool_calls` 的那轮**不发轮次收口事件**，等下一轮 `message_done` 到达时缓冲区被直接清空，这段文字从未固化成消息。
3. **实时 ≠ 刷新**：上述内容其实已落库（`loop.py` 在派发工具前就写了 assistant 行），刷新走历史接口反而能看到。同一次执行，两种看法不一致。

确认卡（写入确认／重启预览）走的是完全相同的机制（`pendingConfirm` + hub 的 `pending_confirms`），缺陷一模一样。

值得解决的理由：问答是 Agent 与人协作的主要交互点，答完即失忆意味着用户无法回看自己做过什么决定、模型基于什么假设继续；而「刷新才回来」会让人怀疑数据是否真的保存了。

## 2. 方案概述

把提问卡与确认卡的**唯一真源改判为消息流自身的那对行**：调用行给出题目与参数，结果行给出答案与批准结果。卡片状态由这对行的存在性决定，不再由挂起态字段驱动。

- **卡片状态机**：只有调用行 = **待答态**（可交互）；结果行到达 = **已答态**（只读留痕）；结果行为中断标记 = **已中断态**（只读）。
- **前端收口成一个纯归一化函数**：实时事件形状（`name/args/result`）与历史行形状（`tool_name/tool_args/tool_result`）都先归一化成同一个渲染模型，卡片判定沿用 `isPreviewCard` 已验证过的「一次调用 = 两条消息行」配对模式。删除 `pendingAsk`/`pendingConfirm` 及它们在消息流底部的独立渲染。
- **后端每轮收口**：在派发工具之前，把本轮已流式输出的文字固化下发（content 为空则不发，避免空行）。执行终态仍只由 `status` 事件判定。
- **数据永远成对**：中断时给挂起的提问与确认补写一条配对结果行，**并补发同样的 `tool_call`/`tool_result` 两个事件**（不补发则实时流比刷新后的历史少一条记录，同构不变式就此破功）。前端据结果行渲染「已中断」。孤儿调用行不再可能出现，刷新后自然不会复活成死卡。
- **hub 的提问卡补发删除**：待答的提问由消息流原样重建，补发成为冗余。挂起用的 future 表保留（watchdog 依赖它判定「等人不算卡死」）。
- **确认卡是真源的一处例外**：「本次调用需要确认」这个事实不在任何消息行里——它取决于写入确认开关与预览重启的运行时判据，前端无法从 `write_file` 的调用行推断它是在等确认、正在跑、还是已跑完。所以确认侧的补发保留，`confirm_request` 事件从「卡片的数据源」降级为「标记哪一行在等确认」，卡片内容仍一律从消息行读。

## 3. 用户故事

### 问答留痕

1. 模型发起提问时，提问卡出现在消息流的**当前位置**（它前面那条助手消息之后），不再是浮在消息流底部的独立控件。题目、选项、人工回答输入框、「取消执行／不再提问，自行决定／提交回答」三个按钮与现状一致。
2. 提交回答后，卡片**原地**转只读：题目完整保留；所有选项仍在，选中项高亮并带对勾、未选中项灰显；手输文本原文附在选项区下方；输入框与三个按钮全部消失；卡头标注「已回答」。
3. 多选题的已答态同时高亮多个选中项，与提交时的勾选一致。
4. 点「不再提问，自行决定」后，卡片转只读并单独标注「自行决定」，与普通回答在视觉上可区分。**（推迟：`declineAsk` 与单题版卡片不在 HEAD 上，随确认卡一批实现）**
5. 提问仍挂起（尚未回答）时刷新页面、切走再切回、或另开标签页连入同一会话，卡片以**待答态**重现，可正常选项、输入、提交；提交后本轮照常继续执行。
6. 已答之后刷新页面、切走再切回，已答卡按同样的只读形态重现，题目与答案与答完当时逐字一致。
7. 同一次执行里模型多次提问，消息流里按发生顺序留下多张已答卡，互不覆盖、不错位。
8. 用户点「停止」中断一次挂起的提问后，卡片转只读「已中断」态；刷新后它仍是「已中断」，不会复活成可交互的死卡。

### 中间文本不丢

9. 模型在提问前输出的说明文字，在提问卡出现之前就已固化成一条助手消息，停在卡片上方；问答答完、本轮继续、直至执行结束，这段文字始终留在消息流里。
10. 同一次执行里每一轮的说明文字各自固化成一条助手消息，先后顺序与模型输出顺序一致。
11. 纯工具调用、没有任何说明文字的那一轮，不产生空的助手消息行。
12. 带思考留痕（reasoning）的轮次，思考块随该轮文字一起固化，不串到下一轮。
13. 刷新后，第 9／10 条看到的文字与实时看到的逐字一致、相对位置一致。

### 确认卡同构

> 本组 4 条（14–17）随切片 006 推迟：确认卡的「本次调用需要确认」不在任何消息行里，需要一套标记与补发机制，而 HEAD 上尚不存在（见 §7）。

14. 写入确认卡批准或拒绝后原地转只读，留下「已批准／已拒绝 + 工具名 + 参数摘要」；参数摘要沿用现有超长截断口径。
15. 重启预览确认卡批准后原地转只读，留下「已确认重启」与前端按工具名生成的人话文案；取消则留「已取消」。文案不依赖后端事件里的 `summary`——那个字段不落消息行，用了就会让刷新前后叉开。
16. 确认卡挂起时刷新页面，以待答态重现，可正常批准或拒绝，且不会重复弹第二张卡。
17. 已答／已驳的确认卡刷新后按只读态重现。

### 同构不变式

18. 任意一次执行结束后，实时流渲染出的消息序列与刷新后历史渲染出的消息序列**同构**：逐条的角色、内容、卡片状态、先后顺序一致。
19. 问答与确认卡之外的工具（读文件、跑命令、预览三件套、待办卡）渲染行为不变：预览卡仍是预览卡，待办仍是待办卡，其余仍落回折叠 JSON 块。**一处有意的可见变化**：一次工具调用在实时流里从「参数块 + 结果块」两个折叠块合并成一个（参数与结果同体），与刷新后一致——这是同构不变式强制的，不是回归。附带收益：待办卡与工具参数在刷新后也能渲染了（此前历史里的参数在 assistant 行上，组件读不到）。

## 4. 已定决策

| 决策点 | 结论 | 被否决的备选 |
|---|---|---|
| 修复范围 | 三个缺口全修 | 只修留痕／只修文本丢失 |
| 留痕形态 | 只读提问卡，原地转灰 | 转两条普通气泡／只美化工具块摘要 |
| 已答态信息密度 | 保留全部选项，选中项高亮 | 只显选中项其余折叠／压成一行摘要 |
| 卡片数据真源 | 复用现有调用行 + 结果行 | 新增专用事件与角色行／纯前端本地合成 |
| 待答态定义 | 提问卡只认工具行（删挂起态字段与提问补发）；确认卡保留补发，但只作「哪一行在等确认」的标记 | 挂起态降为开关／实时照旧只补历史 |
| 中间文本收口 | 后端工具轮补发轮次收口事件 | 前端在 `tool_call` 时固化／新增 `round_end` |
| 确认卡 | 一并修，与提问卡同构 | 只管问答／只美化摘要 |
| 中断死卡 | 后端补写配对结果行 | 前端加执行态闸／两道都做 |
| 验收层级 | 写「实时 ≡ 历史」同构断言 | 只修既有测试 + 手工验证 |

## 5. 测试决策

**接缝优先复用已有的两个，不新建第三个：**

- **后端接缝 `tests/test_agent_loop.py::run_once`** —— 它一次同时给出**事件日志**与 **DB 行**（返回 `sid, status, events, sf`），是本次变更最高的单一接缝，同构不变式的一半在这里断言：
  - 工具轮的轮次收口事件排在 `tool_call` 之前；
  - content 为空的那一轮不发收口事件、不产生空 assistant 行；
  - 每个带 `tool_calls` 的 assistant 行都有配对的 tool 行（含中断补写的那条）；
  - 中断挂起提问后，结果行存在且带中断标记。
- **前端接缝 `applyEvent` + `normalizeMessages`** —— 归一化最终落在**渲染层**（`ChatMessages` 的 computed）而非 `openSession`：`store.messages` 里的 `client_msg_id`/`queued` 是 busy 回滚与插话角标要用的活字段，在 store 层投影掉会打断它们。同构断言因此落在 `frontend/src/stores/messageModel.test.js`：把一段脚本化事件日志喂给 `applyEvent`、把对应的 DB 行形状喂给 `normalizeMessages`，两者输出 **deep-equal**。**这条断言就是「实时 ≡ 历史」的可执行形态**，也是本次交付的核心验收物。
- **组件接缝的同构形态** —— `ChatMessages.test.js` 里另有一条更强的断言：同一次问答，实时形状与历史形状挂载出的卡片 HTML **逐字相同**。它同时钉住归一化与已答态渲染两层。
- **组件接缝 `AskUserCard`** —— 已答态渲染：选中项高亮、未选项灰显、手输原文、自行决定标记、无输入框无按钮；待答态行为与现状一致（选项与人工回答互斥）。

**必须跟着改的既有测试**（不改就交不了）：

- `tests/test_ws.py` 里按帧数硬断言的用例：`test_ws_plain_flow` 的固定帧数计数、`test_ws_ask_flow`、以及 `test_ws_steering_*` 中「`message_done` 只有一条」类断言——工具轮补发后一次执行会有多条。
- **凡把轮次收口事件当「执行结束」标志的地方都要改用 `status` 终态判定**：`tests/test_ws.py` 里多处 `while ... if ev["type"] == "message_done": break` 会在工具轮提前跳出，误判执行已结束。
- `test_ws_reconnect_replays_pending_ask` 作废，由「刷新/重连后待答提问从消息流重建」的新用例取代；`test_ws_reconnect_replays_pending_confirm` **保持绿**（确认侧补发不动）。
- `frontend/tests/store.test.js` 中断言 `ask_user` 置 `pendingAsk`、`confirm_request` 置 `pendingConfirm` 的用例。

**「完成」长什么样**：前后端全量测试绿（后端 pytest **必须串行**，并发会死锁并污染结果）；手工各走一遍「提问 → 回答 → 刷新」与「提问 → 停止 → 刷新」，确认已答卡与已中断卡都在，且刷新前后逐字一致。

## 6. 明确不做

- **不动单题提问协议**：`_normalize_questions` 的校验、多题报错重问、`AskUserCard` 的单题渲染都保持现状（工作树里另有未提交改动，属另一件事）。
- **不新增事件类型、不新增消息角色、不改 `message` 表结构、不做数据迁移**。
- **不改确认卡的触发语义**：`agent.write_confirm` 开关与 `need_confirm` 判据原样保留。
- **不动执行终态判定**：`status` 事件仍是 running 的唯一真源；轮次收口事件不承担终态，前端不得拿它复位 running。
- **不改非卡片工具的展示**：折叠 JSON 块继续服务其余工具。
- **不合并两份重复的前端 store 测试**（`frontend/tests/store.test.js` 与 `frontend/src/stores/chat.test.js`）——是独立的一件事。
- **不给老会话补数据**：历史里已存在的孤儿调用行按「已中断」只读态渲染即可，不写迁移脚本。
- **不改附件、插话（steering）、上下文压缩的既有行为**。

## 7. 补充说明

- `isPreviewCard(m, i)` 已经验证过「一次调用在实时流里是两条消息行」的配对判据，新卡片沿用同一模式，不发明新机制。
- 字段形状必须同时认实时与历史两套，**归一化函数是唯一收口点**——任何在组件里就地读 `m.name ?? m.tool_name` 的散点写法都是这次要消灭的东西。
- `hub.ask_futures` / `hub.confirm_futures` **必须保留**：`app/main.py` 的 watchdog 靠它们判定「挂起等人不算卡死」。被删的是提问卡的**载荷**（`pending_asks`，只为补发而存），不是**挂起凭证**；`pending_confirms` 与 `replay_pending` 的确认分支同样保留。
- **确认卡的人话文案改由前端按工具名生成**：后端 `confirm_request` 带的 `summary` 只活在事件里、不落消息行，用它渲染就会让实时与刷新后叉开。同构不变式反过来约束了「哪些信息允许只存在于事件中」——答案是不允许，`summary` 不再参与渲染。
- 中断时补写配对结果行有额外收益：回注模型的历史不会缺 tool 消息，而 tool_calls 与 tool 消息配对是 OpenAI 兼容 API 的硬要求。
- `ChatView.vue` 传给 `ChatMessages` 的 `pendingAsk`/`pendingConfirm` 两个 prop 及对应的滚底 watch 一并移除；卡片进入消息流后，滚底由既有的 `messages.length` watch 覆盖。
- **实现前置**：当前工作树是脏的（`app/agent/llm.py`、`app/agent/loop.py`、`app/agent/prompts.py`、`app/hub.py`、`app/api/ws.py`、`frontend/src/components/AskUserCard.vue`、`frontend/src/stores/chat.js`、`tests/test_ws.py` 均有未提交改动，来自「单题提问」那件事，另有两份未跟踪的 ADR 0027/0028）。动手前必须先确认这些改动的归属与提交状态，避免混提交或互相覆盖。
