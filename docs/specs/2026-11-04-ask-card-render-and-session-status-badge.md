# 提问卡实时渲染修复与会话状态角标

## 问题陈述

演示站观察到两组问题，都发生在聊天页。

**其一，提问卡经常不出现，会话卡死。** Agent 调 `ask_user` 后，聊天流里只有一条
`ask_user` 的通用工具块（折叠 JSON），看不到可作答的提问卡；唯一的回答入口不存在，
前端发不出 `ask_submit`，后端 `hub.ask` 的 future 与 `hub.running` 永久挂起
（未配置超时即无限等）。用户必须切到别的会话再切回来，卡片才出现。同理，已经回答过的
提问卡在切换会话后也会消失，退化成通用工具块。

已确认的根因：

- 模型偶尔把 `questions` 参数二次编码成 JSON 字符串。后端 `_normalize_questions` 已容错
  （e4a2a02），前端 `askQuestionsOf` 只认数组或顶层 `question`，拿不到题目，`isAskCard`
  为假，落回 `ToolCallBlock`。
- 历史行保存的是模型原始 `tool_args`，重建已答卡时同样经过 `askQuestionsOf`；同一份坏参数
  在刷新/切会话后再次丢失卡片。
- 实时流里 `tool_call` 先建行，随后 `ask_user` 事件虽带后端规整后的 `questions`，但
  `applyEvent` 发现已有开着的调用行就不做任何更新，规整数据被丢掉。
- 切回会话时，`openSession` 装入历史（待答调用尚无 tool 行）+ `hub.replay_pending` 补发
  `ask_user`，前端才合成一条带规整题目的行——这正是「切走再回来就好了」的原因。

**其二，侧栏看不见别的会话在干什么。** 左侧会话列表只在挂载/增删改时拉一次，接口虽带回
`status` 却没有使用；用户在主会话里跑长流程时，无法一眼看出其他会话是在运行、在等自己回答、
还是已经完成/失败。

## 方案概述

- **提问卡**：前端解析器与后端同口径容错（`questions` 为 JSON 字符串时解析）；实时
  `ask_user` 事件用规整后的题目覆盖已开的调用行；历史与实时都经同一归一化函数，保持
  ADR-0029 的「实时 ≡ 历史」。
- **会话状态角标**：新增按账号汇总的 `GET /api/sessions/live-status`，从 `ChatHub` 内存
  汇总「运行中 / 挂起类型（ask/confirm）/ 最近结果 + 结束时间」；侧栏 5 秒轮询、页面隐藏
  暂停；角标四态（等待黄 > 运行转圈 > 完成绿 / 失败或停止红），绿/红只对本次页面打开后
  结束的执行出现，点击消除并打开会话，不落库。

### 接口与数据形状

`GET /api/sessions/live-status`（必须注册在 `GET /api/sessions/{session_id}` 之前，否则
`live-status` 会被当成 int 路径参数而 422）：

```json
{
  "sessions": [
    {
      "session_id": 12,
      "running": true,
      "waiting": "none",
      "last_outcome": "completed",
      "finished_at": 1762300000.123
    }
  ]
}
```

- 只返回当前账号自己的会话（经 `chat_session` JOIN `workspace.owner_user_id` 收口），
  且只包含至少有一项实时事实（running / waiting / 最近结果）的会话。
- `waiting` 取 `ask`、`confirm`、`none`，同一会话不会同时挂起两处；若都出现，`ask` 优先。
- `last_outcome` 取 `completed`、`cancelled`、`error`、`null`；`finished_at` 为 epoch 秒。
- `running` 来自 `hub.running`（压缩期间也为真）；最近结果只由聊天 run 写入，压缩结束
  不制造绿/红提醒。

后端记录最近结果的方式：

- `ChatHub` 新增 `last_outcome: dict[int, {"outcome": str, "finished_at": float}]`。
- `AgentRunner.run` 内部记录本次结果（`_Cancelled` → `cancelled`，异常 → `error`，正常
  收工 → `completed`），**不改变现有返回值契约**——大量测试断言它返回 `"idle"`/`"error"`。
  由 `run_task` 在 `finally` 读该记录写入 hub，并在新 run 开始时清掉上一条结果。
- 不读数据库 `chat_session.status` 作为角标依据：完成与用户取消最终都落 `idle`，数据库
  本身分不出这两者，且进程重启后的残留值会制造幽灵转圈。

前端形状：

- `frontend/src/api/index.js` 新增 `getSessionLiveStatuses()`。
- 新增轮询组合式函数（与 `useDevStatus` 同款语义）：5 秒自我续期的 `setTimeout` 链、
  `document.hidden` 时断链、重新可见立即补一次、失败静默保留上一次读数、卸载清理。
- 侧栏在组件内维护：`pageOpenedAt`（页面打开时刻）、已消除集合（键为
  `session_id:finished_at`）。结束态仅在 `finished_at * 1000 > pageOpenedAt` 且未被消除时
  显示；角标位置在标题右侧、时间左侧。
- 点击任意角标都打开该会话；点击绿/红角标额外写入已消除集合并立即消失。消除只活在本次
  页面内，刷新即忘。

## 用户故事

### A. 提问卡

1. **实时出现**：模型以数组形式给题时，实时流立刻出现提问卡，不需要切换会话。
2. **二次编码容错**：`questions` 被塞成 JSON 字符串（含 `options` 也是字符串）时，实时流
   与切回后的历史都渲染同一张提问卡。
3. **实时覆盖**：`ask_user` 事件到达时若已有开着的 `ask_user` 调用行，用事件里的规整题目
   覆盖该行参数，不新增重复行。
4. **作答闭环**：卡片按钮可用；提交后正常走 `ask_submit`，run 继续，全程不要求切换会话。
5. **待答切回**：回答前切走再切回，`hub.replay_pending` 补发后仍显示同一张待答卡。
6. **已答切回**：回答后切走再切回，历史重建出只读已答卡（含答案/取消/不再提问留痕），
   不退回通用工具块。
7. **空参数保持折叠**：确实没有可解析题目时仍渲染通用工具块，不画一张空卡。
8. **同构**：同一份底层参数分别经实时事件路径与历史行路径归一化后，`ask_user` 行的题目
   字段一致（ADR-0029）。

### B. 会话状态角标

9. **运行中**：任一有活动 run 的会话（含当前正在看的会话）标题右侧显示转圈；run 结束即
   消失（最多滞后一个轮询周期）。
10. **等待操作**：挂起在提问或确认时显示黄色，优先于转圈；回答/确认后回到运行中，直至结束。
11. **已完成**：本次页面打开后结束且结果为 `completed` 的会话显示绿色，保持到点击或刷新。
12. **失败/停止**：结果为 `cancelled` 或 `error` 的会话显示红色，行为同绿色。
13. **点击**：点击任意角标打开该会话；绿/红点击后消除，本页不再出现；运行/等待角标点击
    不消除（状态仍真实存在）。
14. **页面级**：刷新不保留消除记录；页面打开前已结束的执行不补提醒；后端进程重启后状态
    清空（内存态）。
15. **优先级唯一**：同一会话同时刻只显示一个角标，等待 > 运行 > 结束态。
16. **隔离与不干扰**：只返回当前账号自己的会话；不新增 WebSocket、不写数据库、不影响
    会话排序/标题/删除。

## 已定决策

- 提问卡修复覆盖实时与历史两条路径，并补回归测试；不只修其中一侧。
- 容错只做在显示层，不把规整后的题目回写数据库里的模型原始参数。
- 不做「参数为空时从上下文猜问题」的兜底；解析不出题目就保持通用工具块。
- 角标覆盖所有会话，包含当前正在看的会话。
- 异常与用户停止统一用红色图标，点击消除。
- 结束提醒仅本次页面有效，刷新即忘，不落库、不跨设备。
- 状态数据源用 5 秒轮询的专用接口，不为它另开第二条 WebSocket（ADR-0041）。
- 图标位置固定在标题右侧、时间左侧。
- 黄色同时覆盖提问与确认两种挂起。
- 点击结束态角标 = 消除并打开该会话。
- 运行/挂起状态取 hub 内存，不读数据库 `chat_session.status`。
- 最近结果由 runner 记录，保持 `AgentRunner.run` 现有返回契约不变。
- 结束态判定用「结束时间晚于页面打开时间」，不用「轮询是否观察到 running」，短执行不会漏。
- 不改变 `listSessions` 的返回结构，角标数据走独立接口。

## 测试决策

后端（pytest 必须串行，共享 `zerocode_test` 库）：

- `tests/test_sessions.py`
  - `live-status` 返回形状与账号隔离：他人会话不出现；无实时事实的会话不出现。
  - 数据库中 `status='idle'` 但 hub 标记 running 时，接口仍返回 `running=true`（钉住
    「不读 DB 状态」）。
  - 同时挂起 ask/confirm 时 `waiting` 的优先级；最近结果与 `finished_at` 透传。
  - 路由顺序：请求 `/api/sessions/live-status` 不落进 `{session_id}` 而 422。
- `tests/test_ws.py`
  - run 正常结束写入 `completed` + `finished_at`；新 run 开始时清掉旧结果。
  - 用户取消写入 `cancelled`（数据库状态仍为 `idle`，既有断言不变）。
  - 异常结束写入 `error`。
- 既有 `test_agent_loop.py` 对 `run()` 返回 `"idle"` 的断言保持不变。

前端（`vitest --maxWorkers=4`）：

- `messageModel.test.js`：`askQuestionsOf` 对 JSON 字符串、双重编码 options、顶层
  `question` 旧形状、非法字符串、空参数的输出。
- `chat.test.js`：`applyEvent('ask_user')` 覆盖已开行、补发时合成行、实时与历史归一化同构。
- `ChatMessages.test.js`：字符串编码参数渲染出提问卡；已答态只读。
- `SideBar.test.js`：四态与优先级、位置（标题与时间之间）、当前会话也显示、点击结束态
  消除并打开、点击运行态只打开、页面打开前结束不提醒、刷新后消除记录不保留；接口失败
  静默保留旧读数。
- 轮询组合式函数（新增测试文件）：5 秒续期、隐藏暂停、可见立即补一次、卸载清理。

完成标准：新增/相关用例全绿，既有 `test_ws.py`、`test_sessions.py`、聊天前端用例无回归；
手工确认「实时出卡 → 直接作答 → 切走切回仍是已答卡」与角标四态在演示站可用。

## 明确不做

- 不加全局 WS/SSE 推送会话状态。
- 不做服务端已读标记、跨设备同步或历史提醒。
- 不新增数据库列/表，不修改 `chat_session.status` 语义。
- 不为 `ask_user` 增加超时、自动回答或自动恢复。
- 不做浏览器通知、声音、任务栏提醒。
- 不改侧栏排序、折叠、虚拟列表等既有逻辑。
- 不覆盖移动端（uni-app 移动栈）的会话列表；如需要另行立项。
- 不做应用级、工作区级汇总角标。

## 补充说明

- 角标取舍已记录在 `docs/adr/0041-session-status-badge-polling-page-scoped.md`；术语
  （会话状态角标 / 等待操作 / 页面级提醒 / 实时会话状态 / 最近结果 / 待答补发）以
  `CONTEXT.md` 为准。
- 页面打开时刻取浏览器 epoch，与后端 `finished_at` 比较，前提是两端时钟大致同步（NTP）；
  若演示机时钟明显漂移，结束态判定会随之偏移。
- 多标签页各自维护消除集合，互不影响（页面级提醒的预期行为）。
- 进程重启会同时丢失待答补发与最近结果，界面回到「无角标」；这与既有 `hub` 内存态代价
  一致，不为它加持久化。
- 演示站生效仍需重新出包并重建前后端镜像，属于独立部署动作，需另行确认。
