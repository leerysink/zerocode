# 聊天页打开大会话的加载延迟优化

## 问题陈述

演示站（公网访问）里，在左侧侧栏点击一个消息量大的会话，中栏要空等约 3 秒才出现内容；
等待期间标题与侧栏高亮已切到新会话，中栏却还留着**上一个会话**的消息，容易被当成
「点错了」或「新会话是空的」。

已在开发库核实的事实（2026-11-09）：

- 最大会话 485 条消息，`GET /api/sessions/{id}/messages` 的响应体约 **950 KB**，其中
  878 KB 来自 `tool_result`；同一条 SQL 在库上仅 **7 ms**——慢不在数据库。
- 全站**没有启用 gzip**：平台控制台由 FastAPI 直接托管（不起 nginx），`app/main.py`
  未挂任何压缩中间件，950 KB 文本原样跨公网传输。
- `store.openSession` 先 `await getMessages`、**再串行** `await getSessionDetail`，
  两者都回来才 `this.messages = data`（[frontend/src/stores/chat.js:299](../../frontend/src/stores/chat.js)）。
  串行往返 + 未压缩首包叠加，构成主要等待。
- 等待期间不清旧消息：`currentSessionId` 已切换，`messages` 仍是旧会话，直到新数据到达
  才整体替换。
- 切走再切回同一会话没有任何缓存，重新拉取、重新解析、重新渲染，成本每次全额支付。
- 数据到达后中栏是一次性同步渲染全部历史（Markdown + 代码高亮 + 工具卡）；体感上主要
  表现为「等待」，但大会话铺开那一瞬仍有可测的渲染长任务。

## 方案概述

- **传输**：FastAPI 挂 `GZipMiddleware`（`minimum_size=1024`、`compresslevel=6`），
  消息响应在客户端声明 `Accept-Encoding: gzip` 时压缩传输；不改任何接口契约与返回结构。
- **请求链**：`openSession` 把 `getMessages` 与 `getSessionDetail` 改为并行；消息一到就
  渲染，detail 后到只补 todo / 模型状态。
- **切换瞬间**：未缓存会话立即清空中栏并显示轻量加载态；已缓存会话立即显示缓存内容。
- **缓存**：会话级内存缓存（本页面有效、刷新即失效，按最近使用保留 5 个会话），切回
  同一会话瞬时显示，后台静默拉新并替换。
- **渲染**：消息超过阈值时先渲染**最近 80 条**，其余在空闲帧分批前插补齐，用户无需任何
  额外操作；不足 80 条的会话行为与现状一致。

### 接缝

优先复用已有接缝，变更集中在三处：

1. **HTTP 边界**（`GET /api/sessions/{id}/messages`）：压缩由中间件透明完成，测试打在
   `TestClient` 层（响应头 + 解压后 JSON 等价），业务代码零改动。
2. **`useChatStore.openSession`**：所有装载路径的唯一入口（侧栏点击、新建会话、角标点击
   都走它）。并行顺序、缓存读写、失败处理、WS 连接时点都在这里，测试直接用 mock api
   调 store 断言。
3. **`ChatMessages` 的渲染窗口**：把「取最近 N 条 + 分批补齐」抽成纯逻辑
   （`windowOf(view, size)` 或等价组合式函数），happy-dom 下断言切片与补齐顺序；组件只
   接线与滚动锚定。

`messageModel.normalizeMessages`、`promptRailModel` 不改：导航条对「缺量测」的提问本来
就不画横杠（[frontend/src/stores/promptRailModel.js](../../frontend/src/stores/promptRailModel.js) 第 61 行），
分批渲染天然兼容。

## 用户故事

### A. 传输

1. **压缩生效**：请求头带 `Accept-Encoding: gzip` 时，消息接口响应带
   `Content-Encoding: gzip`，解压后与未压缩响应逐字等价。
2. **小响应不压缩**：响应体小于 1 KB（如单会话详情）不压缩，行为与现状一致。
3. **不声明 gzip 的客户端**：请求未带 `Accept-Encoding: gzip` 时返回未压缩明文，
   兼容旧客户端与调试工具。
4. **全接口透明**：压缩对静态资源与其它 JSON 接口同样生效，不改变任何路由、状态码与
   返回结构。

### B. 打开会话（请求链）

5. **并行**：点击会话后，消息与会话详情两个请求同时发出，不再串行等待。
6. **消息先到先显**：`getMessages` 返回即渲染消息；`getSessionDetail` 后到时只回填
   todo、模型与视觉能力，不阻塞、不重排消息。
7. **WS 连接时点**：WebSocket 在**历史消息装入之后**才连接，保证 hub 补发的待答
   `ask_user` / `confirm_request` 不会先到、又被随后的历史替换掉（ADR-0029 的「待答
   补发」不能丢）。
8. **竞态**：快速连续点击多个会话时，先发起但后返回的响应不得覆盖当前会话（沿用现有
   `currentSessionId !== id` 守卫，缓存写入也要过同一道闸）。
9. **失败可重试**：消息请求失败时不抛未处理异常；无缓存时中栏显示加载失败提示，用户
   再次点击该会话即可重试；有缓存时保留缓存内容并提示刷新失败。

### C. 切换瞬间与缓存

10. **未缓存会话**：点下即清空上一个会话的消息，中栏显示轻量加载态（骨架/提示），
    侧栏高亮与标题立即切换。
11. **已缓存会话**：点下立即显示缓存内容并回到交互可用状态；同时后台拉取最新历史，
    到达后原地替换。
12. **缓存范围**：仅本次页面内存有效，刷新浏览器即失效；不写 localStorage、不跨标签页。
13. **缓存上限**：按最近使用保留最多 5 个会话；超出时淘汰最久未使用的。
14. **缓存失效**：删除会话时清掉其缓存；同一会话的实时 WS 事件只作用于当前会话，
    不影响其它会话的缓存快照。

### D. 大会话渲染

15. **首屏 80 条**：归一化后消息条数超过 80 时，首帧只渲染最近 80 条，并滚动到底部
    （与现状一致）。
16. **空闲补齐**：其余消息在空闲帧分批前插，直到全部渲染；补齐过程不改变用户当前
    阅读位置（前插多少高度，`scrollTop` 相应加多少）。
17. **无需交互**：补齐对用户不可见，不出现「加载更早」按钮或任何点击要求。
18. **小会话无差别**：≤80 条的会话一次性渲染，行为与现状完全一致。
19. **提问导航条**：只对已渲染的提问画横杠；分批补齐后自动重测，最终恢复为全部提问。
20. **流式不变**：`streamingContent` / `streamingThinking` 的增量渲染与自动滚底策略不变。

### E. 验收

21. **时延**：在线上环境打开最大会话（485 条 / 约 950 KB）时，首条内容可见 ≤ 1s，
    整段铺开 ≤ 2s，切换过程无长冻结。
22. **回归**：待答卡/确认卡切回、流式输出、提问导航条跳转、失败重试均与现状一致。

## 已定决策

- 只加压缩，**不改消息接口的返回结构**：不分页、不做工具结果按需加载、不删字段。
- 压缩放在 FastAPI 中间件，不改网关（平台控制台不经中央网关，网关只服务应用子域名）。
- 不新增接口，不改数据库。
- 两个请求并行，消息先到先渲染；detail 失败静默降级（保持现状）。
- WS 连接保持在历史装入之后，优先保证待答补发不丢。
- 未缓存会话切换时立即清空旧内容并显示加载态，不做「旧内容 + 遮罩」。
- 缓存只活在本页内存，保留最近 5 个会话，不做滚动位置恢复。
- 大会话首屏 80 条、空闲补齐；不做虚拟滚动、不做手动「加载更早」。
- 验收以线上最大会话为样本，首内容 ≤1s、铺开 ≤2s。

## 明确不做

- 不做虚拟滚动（现有滚动、导航条量测与流式跟随都不动）。
- 不做消息分页、不做大工具结果按需加载、不改接口返回结构。
- 不做滚动位置恢复（按共识不选这一档）。
- 不改 WebSocket 协议、不改待答补发语义。
- 不改文件面板、待办条、输入框等其它区域的加载逻辑。

## 补充说明

- 压缩是全站收益：除消息接口外，前端静态资源同样受益；`GZipMiddleware` 在无
  `StreamingResponse` 的项目里没有 SSE 缓冲风险（已确认全仓无 SSE）。
- 压缩成本可控：所装 Starlette 的 `GZipMiddleware` 对 ≥128 KiB 的响应在线程池里压缩，
  不占事件循环；950 KB JSON 实测压到约 194 KB。`compresslevel` 取 6 而非默认 9，换取
  延迟与 CPU。中间件本身已排除 `image/*`、`video/*`、`application/zip` 与 206 响应。
- 首包体积仍约 950 KB（gzip 后约百 KB 级），若后续仍不达标，下一步才是接口瘦身
  （分页或按需加载工具结果），本次刻意留到那时再评估。
- 缓存快照与 WS 事件的一致性由「只为当前会话建连」保证：切走即断连，缓存是断连时刻
  的只读快照，切回先显示、再由最新历史替换。
