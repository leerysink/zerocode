# 需求澄清模式（clarify mode）

日期：2026-11-01 ｜ 关联：ADR-0032（门禁机制）、ADR-0033（文档落点与回灌）｜ 术语：`CONTEXT.md`

## 1. 问题陈述

平台 Agent 拿到一句话需求就直接开工。系统提示词里早就有「需求含糊、有多种合理方案、信息缺失时立即
提问，不要替用户假设」（`prompts.py` 规则 4），但它是软约束，靠模型自觉，实际不生效——用户体感是
「提问太少、了解不清晰」。第二层缺口在沉淀：即便问清楚了，结论只活在本次会话上下文里，下次会话
照样不知道当初为什么这样定，返工反复发生。

两个缺口都要补：**必须问**（代码门禁，模型绕不过）+ **问完要留下**（工作区文档 + 回灌索引）。

## 2. 方案概述

- **首轮澄清门禁**：`_dispatch` 在放行第一批 `write_file`/`edit_file` 前检查两个信号——本轮至少问过一道
  提问卡，且模型调用过 `clarify_done` 声明对齐完成。缺任一即挡回，返回引导文本让模型先去提问。
- **两段式澄清流程**：细则写进 `build_system_prompt` 的新增段落——先输出结构化解读（需求翻译 / 歧义词候选 /
  动机推测）并用一张提问卡请用户确认无偏差（这张卡算第 1 题），再逐条单题拷问。
- **豁免可审计**：模型可在 `clarify_done` 里声明「需求已明确、无需提问」跳过拷问，但必传一句
  「我对需求的理解是…」，这句话渲染进消息流成为可见留痕。
- **软目标 + 代码止损**：提问预算「通常 3~5 题」写在 prompt 里；不设硬上限，改为第 6 次提问时由后端
  注入一条止损提醒（提醒不拒绝调用）。
- **决策落文档**：澄清结论写进应用工作区 `docs/adr/`（决策）与 `docs/specs/`（计划）；写前用提问卡征询，
  同意后落在 `docs/` 的本次写入免二次 `write_confirm`。
- **决策索引回灌**：每轮拼装扫描这两个目录，把「文件名 + 标题 + 摘要」注入 system 尾部，正文按需 `read_file`。
- **账户级开关**：新配置前缀 `clarify.*` 进 `USER_PREFIXES`，平台级行默认开。

## 3. 接缝（seam）

改动刻意只跨两个既有接缝，不新造测试面：

| 接缝 | 位置 | 承担什么 |
|---|---|---|
| `_dispatch` | `app/agent/loop.py` | 唯一工具派发口，门禁、`clarify_done` 派发都在这里；已有 `test_agent_loop.py` 用 FakeLLM 打这一层 |
| `run_state` | `app/agent/tools.py` 的 `ToolContext` | 单次 run 的计数容器（`preview_restarts`/`browser_checks` 已用），放提问计数与门禁状态，不落库 |
| `_build_messages` | `app/agent/loop.py` | 所有 system 尾部注入段的唯一出口（`<context_summary>`/`<current_todos>`/`<memories>` 同构），决策索引走这里 |
| 门禁判定 | 新纯函数 `clarification_state(...)`（建议落在 `app/agent/clarify.py`） | 输入「本轮事实」输出「放行/拦截+原因」，无 IO，直接单测 |

会话级解除标记存 `ChatHub`（内存态，与挂起点同性质：进程重启即失效，这是既有代价，不额外发明持久层）。

## 4. 用户故事

每条可独立验证。默认前提：`clarify.enabled = true`。

1. **门禁拦下未澄清的写入**：新会话里用户发「给首页加个按钮」，模型第一个动作直接 `write_file` →
   工具返回拦截结果（含「请先用 ask_user 澄清」的引导），磁盘上文件未被创建。
2. **只读工具不受门禁影响**：同上场景，模型先 `list_dir`/`read_file`/`db_query` → 全部正常执行。
   否则模型在门禁内无法完成澄清。
3. **提问后放行**：模型 `ask_user` 得到用户回答 → 调 `clarify_done` → 再 `write_file` → 正常写入。
4. **串联判据缺一即拦**：只问过 `ask_user` 没调 `clarify_done` → 拦；只调了 `clarify_done`
   （`basis=clarified`）但本轮从未提问 → 拦。
5. **豁免直通**：模型调 `clarify_done(basis="already_clear", understanding="把 README 标题改为 X")`
   且本轮未提问 → 放行，不强迫它编一道无意义的问题。
6. **豁免可见**：故事 5 的 `understanding` 落进工具结果行，聊天页渲染为「✓ 需求已对齐：<理解>」；
   刷新页面后该行原样重建（ADR-0029「实时 ≡ 历史」）。
7. **自行决定解除本会话**：用户点提问卡的「不再提问，自行决定」→ **本会话**后续新任务不再被门禁拦，
   也不需要 `clarify_done`。
8. **软目标进 prompt**：开启模式下 system 里能读到「通常 3~5 题应收口」的表述（`test_prompts.py` 断言）。
9. **第 6 题止损提醒**：同一 run 内第 6 次 `ask_user` 时，回注给模型的消息里带一条止损提醒；
   第 5 次不带；提醒不拒绝调用、不改变提问卡本身的正常回答路径。
10. **两段式流程在场**：开启模式下 system 含需求澄清段落，且写明「先出解读块、请用户确认无偏差、
    该确认卡算第 1 题」；关闭模式下整段不注入。
11. **默认开**：平台 `app_config` 有 `clarify.enabled = true`（owner NULL），任何账户无需配置即生效。
12. **账户级关闭**：某账户写 `clarify.enabled = false` 只影响自己——另一账户仍被门禁拦
    （`test_isolation_config_models.py` 形状）。
13. **写文档前征询**：澄清收口后，模型用提问卡问「要不要把计划写成 `docs/specs/*.md`」，
    用户同意才写。
14. **docs 免二次确认**：免确认条件是两个**机器可判**的事实，不猜语义——本轮问过至少一道题
    （同意确实发生在提问卡里），且 `write_file` 的目标是 `docs/` 下的**新建**文件（用户点头的范围是
    「新建这一份」）。同一次 `write_file` 落在 `backend/` 下、或覆盖一份已存在的 `docs/adr/*.md`，
    都照旧弹确认卡。围栏必须是硬路径前缀判定，不可被参数绕过
    （`docs/../backend/x` 这类写法经归一化后首段不再是 docs，不免确认）。
15. **决策索引注入**：工作区有 `docs/adr/*.md` 与 `docs/specs/*.md` 时，system 尾部出现
    `<app_decisions>` 段，每行是「文件名 + 标题 + 一句话摘要」；目录为空或不存在时**不注入空块**
    （与 `<memories>` 同规矩）。
16. **索引有上限**：命中条目超过上限（默认 12）时截断，且不因此报错；摘要取 frontmatter
    `title`/首段，读不到就退化为文件名，不抛异常。
17. **市场包不带 docs**：`apps/<slug>/docs/` 有文件时，市场打包产物里不含 `docs/`
    （`EXCLUDE_TOP` 生效，与 `README.md`/`deploy`/`sqlchange` 同类）。
18. **契约认识 docs**：应用工作区的契约文本目录清单里出现 `docs/`，让 Agent 知道该目录的用途。
19. **应用内 ADR 取号**：模型写 `docs/adr/` 时先 `list_dir` 取下一个 `NNNN-` 序号，与 `sqlchange/`
    的取号规矩同构（prompt 约束，不新增工具）。
20. **关闭开关后一切如旧**：`clarify.enabled = false` 时——门禁不拦、`clarify_done` 不出现也不报错、
    澄清段不注入、止损提醒不触发。只保留故事 15/17/18（文档回灌与打包身份与开关无关）。

## 5. 已定决策

全部来自 2026-11-01 拷问式对齐，翻案需重开 ADR：

| # | 议题 | 裁定 |
|---|---|---|
| 1 | 约束力度 | 首轮门禁（硬约束），不是纯指令加强 |
| 2 | 放行判据 | 串联：本轮 ≥1 次提问留痕 **且** `clarify_done` |
| 3 | 豁免 | 模型自声明 `basis=already_clear`，必传 `understanding` 且前端可见 |
| 4 | 回显形态 | 工具行 + 人话标题，不新建「澄清结论卡」 |
| 5 | 流程形态 | 两段式（解读块 + 确认卡算第 1 题 → 逐条单题） |
| 6 | 提问预算 | 软目标 3~5 题；无硬上限；第 6 次注入止损提醒（阈值可配） |
| 7 | 细则载体 | `build_system_prompt` 段落，不进技能库（技能用户可删） |
| 8 | 开关 | 新前缀 `clarify.*` 进 `USER_PREFIXES`，账户级可关；不碰 `agent.*` 平台级共享的旧裁定 |
| 9 | 文档落点 | `apps/<slug>/docs/adr` + `docs/specs` |
| 10 | 写入通道 | 提问卡征询 → `docs/` 免二次 `write_confirm` |
| 11 | 回灌 | `<app_decisions>` 索引注入，正文按需 `read_file` |
| 12 | 打包身份 | `docs` 进 `EXCLUDE_TOP`（黑名单制下不声明即进包） |
| 13 | 取号 | `NNNN-kebab.md`，写前 `list_dir`；模板不预置 `docs/` |
| 14 | 持久性 | 接受「应用删除后目录成孤儿、平台召不回」；不做快照与导出提醒 |
| 15 | 上线 | 全平台默认开，不灰度（唯一不可回滚项，风险已确认） |

## 6. 测试决策

- **主接缝是 `_dispatch`**，用既有 FakeLLM 驱动（`tests/test_agent_loop.py`）。门禁判定另做纯函数单测，
  把「本轮事实 → 放行/拦截」的矩阵一次覆盖完，不靠拼对话模拟。
- **必须串行的既有约束**：后端测试打到共享 `zerocode_test` 库，**必须串行跑**，并发会 TRUNCATE 死锁；
  被污染的测试结果作废。
- **FakeLLM 与 Spy 签名同步**：给 runner/工具加参数时同步改桩，否则 `tests/test_ws.py` 静默挂死（既有踩坑）。
- **配置隔离**：`clarify.*` 进 `USER_PREFIXES` 后补 `test_isolation_config_models.py` 场景——
  平台行打底、用户行覆盖、他人不受影响。
- **前端 vitest**：`ChatMessages` 渲染 `clarify_done` 的人话标题；`AskUserCard`/`chat.js` 的
  「自行决定」上行带机器可读标记；用全量 `--maxWorkers=4`（默认 60 worker 会偶发超时假失败）。
- **打包**：`docs/` 出现在工作区时市场包内不含该目录，断言走既有包清单测试。
- **「完成」长这样**：故事 1–20 各有对应用例；实时流与刷新后历史同构的不变式对故事 6 单独断言。

## 7. 明确不做

- 不改 `ask_user` 的单题协议（不恢复批量多题）。
- 不做「澄清结论卡」这类新卡片组件；不新增 `doc_write` 专用工具。
- 不在模板里预建 `docs/` 目录；不动 `releases/` 快照逻辑。
- 不做删除应用时的「文档将被孤立」提醒或导出。
- 不做灰度、不做按角色分桶、不新增会话级开关。
- 不把 `agent.*` 改成账户级（`config_service.py` 里那条「普通用户改 `agent.*` 影响全平台是既定取舍」不动）。
- 不动技能库与 `user_skill` 语义。
- 不做「同一决策双写 memory + 文档」——不一致时没有真源，已否决。

## 8. 补充说明

- **散文匹配是禁区**：「自行决定」目前由前端固定文案常量表达（`frontend/src/stores/messageModel.js` 的
  `DECLINE_ANSWER`）。门禁要识别它，必须让上行带机器可读标记（`ask_submit` 增加 `declined`），
  不能在后端匹配那段中文——ADR-0029 已因同类问题吃过教训。
- **`docs/` 的持久性要说清**：`apps/` 被 gitignore，应用工作区**不是 git 仓库**；
  文档能活多久等于那个目录能活多久。别在对外说明里写成「可被 git 追踪」。
- **两类工作区行为不同**：通用工作区（用户自填 `root_path`、无 `app.json`）不注入应用契约，
  于是故事 18 在那里不成立，`docs/` 只靠故事 15 的回灌被看见。这不是缺陷。
- **孤儿目录是既有问题**：`delete_app` 的 M1 裁定只删记录不删目录，`shutil.rmtree` 只存在于建应用失败的
  回滚路径。`docs/` 不引入新故障，只是让残留更有内容。
- **token 成本可感知**：澄清段细则约每轮都发；决策索引只注入摘要行。上线后值得看一眼平均 system 长度变化。
