# 账号治理：管理员、封禁、按人配额与平台默认

- 日期：2026-11-23
- 来源：`grill-with-docs` 拷问共识（11 条）
- 关联决策：ADR-0067（管理员=创始人）、ADR-0068（配额与平台默认住 app_config 两级）、
  ADR-0069（关闭自助注册改邀请码）、ADR-0070（配额闸钉在服务层起栈单点）
- 关联既有：ADR-0003（本票取代其「实例内开放注册」这一半）、ADR-0050（审批权收口创始人）、
  ADR-0062（控制台四页统一）、Ticket 007（用户级键前缀）、Ticket 003（owner 维度）
- 术语：CONTEXT「管理员」「实例」「平台默认」「账号覆盖」「账号配额」「封禁」「邀请码」
  「首号自举」「治理台」「运营台」「控制台」。「子账号」是禁用词，本票一律写「普通账号」。

## 1. 问题陈述

ADR-0003 的运行假设是「每人本地跑一个实例、实例内敞开注册」。平台如今跑在共享服务器上
（通配域名 + 中央网关 + 演示服 + 小程序分发），假设已经掉了：任何人敲 `POST /api/auth/register`
就能进来占资源，而平台**没有任何治理面**——

- `actor` 表只有一个特权位 `is_founder`，且**没有状态列**：没有人能被挡在门外。
- 唯一的资源天花板是全局端口段（8210–8399，prod 偶 dev 奇，约 94 对，**不分辨账号**，
  `app/deploy/ports.py:15`）。一个人建满，别人全部吃 `端口段已用尽`。
- 一个现存缺陷：注册事务把全局 `llm.*` **划归**创始人（`UPDATE` 而非复制，`app/api/auth.py:63`），
  第二个账号开箱拿不到任何模型配置，不自己填密钥就直连超时。平台没有「谁负责让新人开箱能跑」这件事。

值得做的原因不是加功能，而是治理者已经存在（`is_founder` 在商店审批与四个只读面 bypass 上
已经是平台管理员，见 `app/api/store.py:32`、`app/api/metrics.py:45`、`app/api/db_admin.py:29`、
`app/api/memories.py:40`、`app/api/agent_metrics.py:21`），只是这份权力没有账号治理的出口。

## 2. 方案概述

四件事，一页承载：

1. **身份**：管理员就是 `actor.is_founder`，不加列。既有 founder 判定族直接复用为治理门禁。
2. **入口**：自助注册关门，改**邀请码**发号；`actor` 表为空时免码放行（**首号自举**），
   保住「首注册承接无主存量并当选创始人」那条事务原样不动。
3. **封禁**：`actor` 加封禁时间戳；封禁恒作废该账号全部会话，停不停他运行中的容器栈是
   封禁确认框里的独立勾选项。可解封，不删任何数据。
4. **配额与配置权威**：`app_config` 新开 `quota.` 前缀（用户级、可覆盖），两把闸——
   **创建上限**（名下 `app_project` 行数）与**启动上限**（运行中的容器栈数，dev 与 prod 各计一），
   平台默认 10 / 4，管理员豁免。管理员同时接管 `owner NULL` 的**平台默认**层，
   平台级键的写入从此收口给他。

一页 `/admin` **治理台**承载全部动作，与设置页（对我自己配东西）、运营台（管商店版本行）主语分明。

## 3. 用户故事

### A. 管理员身份

- **US-01**：作为第一个注册的人，我注册成功即成为管理员，无需任何事后升级动作。
- **US-02**：作为管理员，我在 NavRail 看到「治理」入口；普通账号看不到，且直接敲 `/admin`
  URL 也进不去（视图层门禁）。
- **US-03**：作为普通账号，我绕过前端直接调任何治理端点都拿到 403（后端层门禁，不依赖视图）。
- **US-04**：作为平台，管理员既不可移交也不可增员——不存在任何端点能把 `is_founder` 改到
  另一个账号上。

### B. 入口：首号自举与邀请码

- **US-05**：作为空库上的第一个人，我在注册页只填昵称与口令即可注册成功，**不需要邀请码**。
- **US-06**：作为已有账号平台上的访客，我不带码提交注册被拒（403，提示「需要邀请码」），
  不产生任何 `actor` 行。
- **US-07**：作为管理员，我在治理台签出一枚邀请码并把码文本看到一次；列表里它显示为
  未使用状态，码本身此后不再回显明文。
- **US-08**：作为使用者，我用一枚未使用的码注册成功；该码随即转为已使用，第二个人再拿它注册被拒。
- **US-09**：作为管理员，我作废一枚未使用的码，它立刻不能再用；我已无法作废一枚已使用的码（无意义）。
- **US-10**：作为使用者，昵称撞车时我拿到既有的 409「昵称已被占用」，且我用的码**不被核销**
  （失败不消耗名额）。
- **US-11**：作为被封禁的账号，我用正确口令登录被拒（401，提示已被封禁），与「口令不正确」
  同样不泄露昵称存在性的口径不再适用于我——封禁提示本身就是存在性信息，这是刻意的。

### C. 封禁

- **US-12**：作为管理员，我在治理台对某个普通账号执行封禁，填一条理由并确认。
- **US-13**：作为被封禁账号的持有者，我正在用的**所有设备**在下一次请求即掉线（401），
  不必等 cookie 过期。
- **US-14**：作为管理员，封禁确认框里「同时停止其运行中的容器栈」是**默认不勾选**的独立选项；
  我不勾，他的栈继续跑；我勾选，系统对他的 dev 与 prod 栈分别下停止动作。
- **US-15**：作为管理员，我对被封禁账号执行解封，他可以立刻重新登录；解封**不会**替他重启任何栈。
- **US-16**：作为被封禁账号，我的应用、工作区、库、模型配置、技能、记忆**一行都不被删**；
  解封后原样可用。
- **US-17**：作为管理员，治理列表里我一眼看出谁被封（状态可读，不靠 hover 提示）。
- **US-18**：作为管理员，我不能封禁自己（治理台不提供该动作，后端同口径拒绝）。

### D. 账号配额

- **US-19**：作为普通账号，我名下第 11 个应用创建被拒（409），提示带上限数字与我的当前值。
- **US-20**：作为普通账号，我运行中的容器栈已达上限时，再起任何一套栈被拒——覆盖
  `dev/start`、`dev/restart`、`prod/start`、`prod/restart`、**`publish`**、**`rollback`**、
  **`publish-requests/{id}/approve`**（共**七**个入口，最后一个是 ADR-0050 的批准即执行）。
  一个应用同时跑 dev 与 prod 计 2。
- **US-20a**：作为刚好跑满额度的普通账号，我**重启**自己已有的栈应当成功——闸判的是
  「这次动作是否净增一套 running」，该应用该环境已 running 时不占新增额度。否则跑满者
  永远无法重启任何东西，那是把自己锁死而非治理。
- **US-20b**：作为被共享者发起发布、所有者批准（ADR-0050），配额按**应用所有者**判、
  豁免也按所有者的 `is_founder` 判——起的是他的栈、占的是他的资源，与点按钮的人是谁无关。
- **US-21**：作为使用者，「启动数已达上限」在 `publish` 上是**同步拒绝**（受理阶段就 409，
  零事件、不落 `running` 的 `deploy_record`），不是先返回 202 再在发布日志里失败。
- **US-22**：作为管理员，我给某个账号单独设创建/启动上限，只影响他，不动平台默认。
- **US-23**：作为管理员，我下调某账号额度而他当前已超：不追溯、不自动停栈、不删东西，
  他只是在下一次启动前得自己降下来；创建侧同理（已超者不能再建，但不会被要求删）。
- **US-24**：作为管理员，我自己不受两把闸约束，且治理台上「本额度不影响管理员」这句话写明了。
- **US-25**：作为普通账号，我从商店安装应用**计入我的创建数**（安装产物就是一个 `app_project` 行），
  不存在单独的「安装额度」。
- **US-26**：作为管理员，我把某账号额度设为「不限」，此后该闸对该账号不再生效。
- **US-27**：作为普通账号，配额读不到任何行（平台默认缺失或被删）时按**不限**处理，
  即行为与本票上线前完全一致——缺键不炸人。

### E. 平台默认与写权限收口

- **US-28**：作为管理员，我在治理台维护平台默认（`owner NULL` 行）：`llm.*` 打底、
  `agent.*`、`deploy.*`、`store.*`、`quota.*`。
- **US-29**：作为新注册的普通账号，我**不填任何密钥**就能直接开聊——读侧「平台默认打底 +
  账号覆盖」的既有回落语义（`app/services/config_service.py:19`）吃到了管理员配的 `llm.*`。
- **US-30**：作为普通账号，我在设置页改一个平台级键（如 `agent.max_tool_rounds`）被拒（403），
  且该字段在界面上是**只读/置灰**并写明「由管理员统一维护」，不是让我点了才知道不行。
- **US-31**：作为普通账号，我照旧能改自己前缀内的键（`llm.` / `memory.` / `clarify.` /
  `subrun.` / `quota.`），写入落在我自己的 owner 行上。
- **US-32**：作为使用者，我自己的 `llm.*` 覆盖行存在时压过平台默认；我删掉覆盖后回落到平台默认。
- **US-33**：作为平台，`llm.api_key` 这类秘密在**任何**读接口上都仍是掩码形态
  （既有 `config_service.mask`，`app/services/config_service.py:47`），治理台不得新开一条明文出口。

### F. 治理台

- **US-34**：作为管理员，`/admin` 上我一眼看到每个账号的：昵称、是否被封（含封禁时间）、
  已创建应用数 / 创建上限、运行中栈数 / 启动上限、注册时间。
- **US-35**：作为管理员，我在治理台改某人的两个配额数字，保存后他的读数与上限同时更新。
- **US-36**：作为管理员，治理台是 `/admin` 这一个新页，沿用 ADR-0062 的三个薄组件口径
  （`ZcPageHeader` / `ZcEntityCard` / `ZcEmptyState`）与「返回固定回 `/`」。
- **US-37**：作为管理员，我把治理台与运营台分开看：`/store-admin` 仍只管商店版本行，
  账号治理不塞进那一页。
- **US-38**：作为管理员，平台默认配置区的入口在治理台，**不在**设置页另开一份可写视图
  （两处可写会分叉出「谁改的」）。
- **US-39**：作为管理员，我签发/作废邀请码在治理台同一页完成，未使用的码列表可看到剩余名额。

## 5. 测试决策

原则：**复用既有接缝，新增接缝只开两处**（服务层起栈判定、治理端点）。不为每个用户故事造新靶。

- **S1 · 封禁读侧单点 —— `app/store/identity.py:95 by_token`（复用）**
  所有已登录请求都过这一处，它是「掉线」的唯一真源。红线：`by_token` 命中被封 actor 一律返回
  `None`（→ 端点转 401）。断言必须打在 `by_token` 与其 HTTP 投影上，而不是只在 `login` 加检查——
  只拦 `login` 会让已发 cookie 继续有效，那是 US-13 的反例。
  **变异校验**：把封禁判定从 `by_token` 摘掉，`login` 侧检查仍全绿 → 说明接线没被盯住，须补一条
  「已开会话在封禁后立刻 401」的用例。

- **S2 · 入口闸 —— `/api/auth/register` 端到端（复用）**
  首号免码 / 有号要码 / 码核销 / 码不复用 / 昵称 409 不烧码，全部走 HTTP 层（`tests/test_auth_api.py`
  已有夹具）。这一族是本票最值钱的测试：一个端点覆盖了 D8+D9 两个不可逆决策。

- **S3 · 治理动作 —— 新增 `/api/admin/*` 路由（新接缝）**
  封禁/解封/停栈勾选/配额读写/邀请码签发作废，全部只经这组端点测试，不去测内部 SQL。
  每条都跑双身份：管理员 200、普通账号 403（同一份参数表复跑，防门禁漏一处）。

- **S4 · 启动闸 —— 配额判定件 + 受理前同步闸门（新接缝，本票唯一的深件）**
  判定是纯函数（`app/deploy/quota.py`，不依赖 `Request`，服务层与端点层皆可调用），
  **接线位置在受理前的同步闸门**：`_dev_task`（四个 start/restart 共用，`app/api/apps.py:413`）
  与 `_publish_gates`（publish / rollback / 批准发布申请共用）。
  刻意**不放进** `engine.start_dev` / `prod.prod_start` 内部——它们拿不到 actor，
  且会把拒绝埋进后台日志流，违背 US-21 的同步拒绝语义。这是对 ADR-0070 §1 措辞的落地修正。
  七个入口（`dev/start`、`dev/restart`、`prod/start`、`prod/restart`、`publish`、`rollback`、
  `publish-requests/{id}/approve`）**共用同一处判定**。**红线测试必须逐入口各来一条超限被拒**，
  不能只测 `prod/start`——「函数有测试」≠「函数被调用」，`publish` 与 `批准发布申请`
  漏调正是本票要防的绕行面。另两条必测边界：跑满额度者重启已有栈成功（US-20a 净增规则）、
  配额按应用所有者判（US-20b）。
  判定所需的「当前运行栈数」从 `app_project.status_dev/status_prod` 聚合，不引入新计数表。
  `publish`/`rollback` 侧断言状态码是**同步 409**，且零 `deploy_hub` 事件、不落 `running` 的
  `deploy_record`（对齐既有预检契约）。

- **S5 · 配置写权限 —— `config_service.set_many`（复用）**
  平台级键非管理员拒写、用户级前缀写 owner 行、读侧回落顺序（平台默认 → 账号覆盖）三点。
  注意既有语义「传 owner_user_id 时给出用户视图」不变，新增的是**写侧**权限。

- **S6 · 夹具种子 —— `tests/conftest.py:36`（必改，否则测不出平台默认）**
  `actor`/`actor_session` 每轮 `TRUNCATE ... CASCADE`，`app_config` 靠这份硬编码种子重放。
  **`quota.max_apps=10`、`quota.max_running_stacks=4` 两行必须同步补进种子**，
  否则「平台级打底行存在」这个事实在测试里根本不成立，US-27（缺键=不限）与 US-19（默认 10）
  会互相掩盖。同处还需为邀请码表补清库（进 TRUNCATE 名单），否则跨用例串味。

- **S7 · 前端结构断言（复用 vitest 口径）**
  `NavRail`「治理」入口的 `isFounder` 分支、`LoginView` 邀请码字段（首号场景与常态两套）、
  `AdminView` 读数与两个配额输入、`SettingsView` 平台级字段变**只读**。
  全量 vitest 用 `--maxWorkers=4`（默认 60 worker 会偶发超时假失败）。

**「完成」长这样**：S1–S7 全绿 + 后端全量 pytest 串行通过（注意它会 down 掉本机在跑的 dev 预览栈，
跑前先与并行会话打招呼）+ 前端手工走一遍「新机器空库首号 → 签码 → 第二人带码注册 →
开箱不填密钥直接开聊 → 建到第 11 个被拒 → 被封后当前设备立刻掉线」。

## 6. 明确不做

- **角色体系**：不建 `role` 列、不做多管理员、不做管理员移交、不做细粒度权限矩阵（D2）。
- **删号**：不提供删除账号及其资源；无「有主 → 回收」路径，`owner_user_id` 外键语义不动（D11）。
- **口令自助**：不做改口令、不做找回密码、不做邮箱验证。邀请码是本票对「口令不经他人之手」
  的补偿手段，不是改口令的替代（ADR-0069）。
- **审计**：不建治理审计表，不记「谁在什么时候改了额度」。封禁留时间戳在 `actor` 上，仅此而已（D17）。
- **强制回收**：不做「下调额度即停栈」的回收器；不做超额账号的定时清理（D12）。
- **配置模板**：不建模板表、不做注册时从模板复制配置；层级仍是「平台默认 + 账号覆盖」两级（D6）。
- **代客覆盖**：管理员不替某个账号写他的用户级覆盖行（治理台改的是该账号的 `quota.` 两行，
  那是限额不是偏好代填）。
- **第三把闸**：不给商店安装单设额度；不把 `max_sessions` 搬进 `quota.`（D5、D25）。
- **dev/prod 分档**：不做「预览额度」与「线上额度」两套数字，启动闸只有一个总数（D4）。
- **反滥用**：不做 IP 限流、设备指纹、注册风控（本票靠入口收口解决，不靠检测）。
- **owner 隔离模型**：ADR-0003 的按账号隔离、ADR-0049 的应用共享、ADR-0050 的发布审批
  全部不动；治理台不提供「替别人操作应用」的动作（除停栈勾选这一项）。

## 7. 补充说明

**迁移与交付物**

- 一个 `changelog/V20261123_01_account_governance.sql`：`actor` 加封禁列（时间戳形态，NULL=未封，
  比布尔位多一个「什么时候封的」且无需布尔陷阱）、新建邀请码表、播 `quota.*` 两行平台默认。
- ADR-0014：`init.sql` 由 changelog **全量合成**且每次发布都在存量库重放——新增的 `INSERT` 种子
  必须带 `ON CONFLICT DO NOTHING`，否则 `scripts/build_output.py` 的重放安全检查会拦下打包。
- 存量库上邀请码表建好即为空，而注册已关门：管理员自己的老账号照常用，
  但要放新人进来必须先登录治理台签码。**上线顺序上这是断点**，需在发布说明里写一句。

**两层天花板并存，本票不去合并口径**

`quota.` 是按账号的软治理，端口段（约 94 对）是全局硬物理顶。配额全开也可能有人撞
`端口段已用尽，请在设置中扩大端口范围`。两条错误文案不同、来源不同，**不得互相冒充**：
配额超限文案要带「你的上限是 N / 管理员可调整」，端口耗尽文案保持原样。

**安全边界**

- 邀请码是新的高价值凭据：泄露一枚未使用的码 = 放开一个注册名额。码明文只在签发响应里出现
  一次，列表回显用掩码或后缀；**不得进后端日志、不得进 `deploy_record.detail`**。
- 口令与 `llm.api_key` 的既有出库约束不破（`app/api/users.py` 只出 id/nickname/is_founder 的
  白名单风格，治理端点照此办理）。
- `GET /api/users`（任一登录账号可读全平台花名册）现状**保持不变**——它不泄露归属关系。
  若本票给它加封禁/配额字段，就必须把该端点升级为管理员专用；否则另开
  `/api/admin/accounts` 承载治理读数，保持 `/api/users` 的最小字段集。**选后者。**

**并发与竞态**

- 首号自举的 `SELECT NOT EXISTS` 判定现状未加锁，本票维持（本地单实例并发抢首号概率极低，
  ADR-0003 原裁定）。关门后这个窗口只剩「新机器空库」一种场景。
- 邀请码核销要在注册事务内做条件更新（`WHERE used_at IS NULL` 的 `UPDATE ... RETURNING`），
  两人同抢一码时只有一人成功，失败方拿 409 且**不消耗码**。

**读数的诚实性**

治理台的「运行中栈数」是 `app_project` 两列状态的投影，不是 `docker ps` 的真值——
容器可能已被外部杀掉而库里仍写 `running`（既有 ADR-0019「端口以容器为准」处理的是反向问题）。
读数旁注一句「以平台记录为准」，不要宣称是宿主实况。

**建议切片顺序（供 `to-tickets`）**

封禁 + 会话吊销（最小可交付，先让治理有牙）→ 邀请码 + 首号自举（入口收口）→
`quota.` 两级 + 创建闸 → 服务层启动闸单点（含 `publish`/`rollback` 六入口）→
平台默认写权限收口 + 新账号开箱可聊 → `/admin` 治理台整合前面各片 → 设置页只读改造。
